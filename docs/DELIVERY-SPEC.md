# 构建、发布与安装规范

规范版本：`0.1.0`；状态：`draft`。

本文面向 CLI、适配器和安装器的实现者，以及发布验收者。读者应了解 Git 版本、构建产物和文件校验。
「必须」「不得」表示验收要求；「建议」表示可说明理由后采用其他方案。

## 目标与适用范围

本规范定义从源码版本到安装后实际运行版本的追溯关系，覆盖 CLI、适配器、插件及配套 Skill。
这里的产品包是具体工具的可安装产物。规范包是本规范的文本、Schema 和示例，两者分别发布。
本文规定交付结果，不规定实现语言，也不要求所有工具采用同一种安装目录。

## 发布场景

发布者从确定的源码提交构建平台包，生成 GitHub Release，再将同一套包上传 SkillHub。
安装者取得获授权的产物，检查来源与完整性，安装后核实 CLI 和实际运行的适配器版本。
升级可能同时涉及磁盘文件和应用中已加载的服务；二者必须分别检查。

## 版本与产物

### DEL-001：发布入口

工具必须以 GitHub Release 记录版本化产物，供 SkillHub 分发。
不得发布到 npm registry；安装流程不得默认依赖 npm。构建阶段可以使用项目声明的构建工具。
私有 Release 的下载必须使用获授权的身份，安装脚本不得内嵌个人令牌。

### DEL-002：确定的源码版本

Release 必须对应不可变的源码提交，并记录 `source_commit`、构建环境和构建步骤。
发布构建不得包含未提交修改。标签名、包版本和 manifest 版本必须一致。
不得用移动标签、分支名或「最新版」代替已发布版本的身份。

### DEL-003：产物一致性

上传 SkillHub 的产品包必须与 Release 包逐字节一致，不得在上传前重新构建或修改内容。
若分发平台重新包装，必须保留原包校验值及包装关系，并验证安装后组件内容一致。
内容发生变化时必须生成新版本，不得静默替换已有版本产物。

### DEL-004：manifest 内容

产品包必须携带符合 [Release manifest Schema](../schemas/release-manifest.schema.json) 的 manifest。
manifest 必须标明规范版本、产品版本、源码提交、目标系统与架构，以及组件路径、角色、版本和 SHA-256。
CLI、适配器、JAR、DLL 等实际交付组件必须逐项列出；不适用的组件无需虚构。

### DEL-005：哈希的边界

组件 SHA-256 用于检查内容一致性，不单独证明发布者身份或可信来源。
包文件的 SHA-256 必须通过独立校验清单记录；组件列表不得包含需要自引用哈希的 manifest。
来源检查必须绑定预期仓库、发布身份和下载入口；只比较同一不可信来源提供的文件与哈希，不算来源验证。

### DEL-006：依赖与兼容范围

manifest 必须声明原应用、插件、协议和 Skill 的兼容范围，并记录安装所需外部运行时。
兼容声明必须说明版本范围、平台、架构及验证证据。未测试的组合必须标为未验证。
许可、驱动或应用安装等外部前提必须可检查，不得将它们宣称为产品包自带能力。

### DEL-007：平台包边界

每个包必须明确目标操作系统与架构，安装器必须在写入前检查目标是否匹配。
不得把某个平台的构建成功外推为其他平台可安装或可运行。
涉及应用进程内加载时，必须检查宿主进程架构；仅检查操作系统架构不够。

## 安装与升级

### DEL-008：先检查后写入

安装器必须先检查包来源、哈希、目标路径、平台、依赖和目标目录现状，再修改安装文件。
包中路径必须解析到声明的安装根目录；绝对路径、路径穿越和越界链接必须拒绝。
失败必须说明是否已写入、已恢复或状态未知，不能以下载完成代表安装成功。

### DEL-009：保护已有内容

安装器只能替换其安装记录明确拥有的文件，必须保留用户配置、工程和其他软件文件。
发现未登记的同名文件时，必须报告冲突并停止覆盖，或使用独立版本目录。
安装器不得递归清理未经核实的目录；卸载同样受文件归属约束。

### DEL-010：升级检查点

升级必须在切换前保留可恢复的旧版本与安装记录，并完整检查候选版本。
多组件包必须作为同一版本集合切换，不能静默留下 CLI、插件和适配器的混合版本。
无法原子切换时必须说明步骤、失败状态与恢复方法；不得假称事务回滚。

### DEL-011：恢复结果

升级失败后，安装器必须验证恢复是否完成，并报告当前磁盘组件版本及应用运行版本。
原应用数据格式已经迁移时，不得假定恢复旧二进制即可恢复工程。
恢复不可执行或不可证明时必须返回未知或需处理状态，并保留诊断信息。

### DEL-012：应用集成边界

默认安装只能完成包自身部署，不得自动改变原应用注册、全局插件配置、许可状态或重启原应用。
需要这些动作时，必须分别描述作用范围、前提及恢复方式，并检查该动作是否已有明确授权。
部署完成、插件已注册、插件已加载和服务可连接必须分别报告。

### DEL-013：版本读回

安装后必须核实 CLI 版本、磁盘适配器版本，以及原应用中实际运行的插件或服务版本。
运行服务必须提供构建身份或可核实的等效证据，不能只回显客户端期望的版本。
服务尚未重载、无法读取身份或不兼容时，不得报告整套工具已就绪。

### DEL-014：诊断与可重试

安装器必须提供可重复运行的版本与健康检查，不因重复检查修改工程或应用配置。
安装日志必须记录阶段、版本和恢复结果，并屏蔽凭证及许可密钥。
重复安装已完成的同一版本，应核验内容并明确结果；不得反复覆盖未知文件。

## SkillHub 分发

### DEL-015：分发阶段独立记录

构建、Release 上传、SkillHub 上传、CLI 登记、Skill 绑定、版本发布和安装验证必须分别记录结果。
某一步成功不得代表后续步骤已成功。平台不存在某一步时必须标明不适用和依据。
自动化凭证必须来自受控配置，不得随产品包或公开日志分发。

### DEL-016：实际安装路径验证

发布者必须验证 SkillHub 的包下载、安装、更新及版本查询能处理产品的实际文件结构。
不得因平台提供 NODE 或 GO 等登记选项，就推断它支持任意原生多文件包。
未验证的上传、登记或安装能力必须列为开放问题；在解决前不得宣称完整分发链路可用。

### DEL-017：Skill 与 CLI 配套

Skill 必须声明兼容的 CLI 与协议版本，并能确认安装后实际版本。
SkillHub 的绑定记录不能代替运行时兼容检查；发现不兼容必须停止依赖该能力的操作。
Skill 和 CLI 分别更新时，必须说明支持的组合，不能把独立版本号当作相同版本要求。

### DEL-018：受控的可见范围

私有仓库和 Release 不自动保证 SkillHub 产物的可见范围。
发布者必须核实分发对象、下载权限与更新权限，凭证失效不得静默切换到未经授权的镜像。
权限检查失败属于分发失败，不能用公开副本绕过。

## 发布验收

### DEL-019：产品发布门禁

稳定产品 Release 必须满足 [验证规范](VERIFICATION-SPEC.md) 中自己声明的能力、版本与环境范围。
稳定版发布者必须从 Release 下载实际包验证安装、版本读回及声明能力的代表性真实操作。
产品声明支持升级或恢复时，稳定发布前必须验证对应路径；不支持的路径必须明确声明。
只有源码测试通过或本地开发目录能运行，不足以证明发布包可用。

### DEL-020：精简的发布记录

每次发布必须保留变更、兼容性变化、已知限制、安装说明和验证证据的入口。
不要求双语 README、公开贡献指南或社区模板；机器契约和运行边界不得随文档精简而删除。
破坏性变化必须指出受影响的调用和迁移方法，不能只写「修复若干问题」。

### DEL-021：草稿与实验发布

`draft` 或 `experimental` 可以形成预发布 Release，允许未完成实测，但必须逐能力记录成熟度与限制。
未完成的检查、升级或恢复路径必须明确记录，不得借用生产稳定版描述或宣称已通过验收。
预发布仍必须保留来源追溯、包身份、目标平台、兼容范围和验证对象声明。
稳定发布只覆盖已声明并完成验收的能力与环境，不代表支持所有应用版本。

### DEL-022：规范包

本规范自身的 Release ZIP 必须包含该版本规范、Schema、示例、变更记录和校验清单。
规范包不得伪装成可执行 CLI 产品，不得仅为分发规范而登记一个 CLI。
规范包上传 SkillHub 时必须验证适合文本规范的资源类型和读取方式；不支持时应保留 Release 交付。

## 异常与待定事项

1. SkillHub 对原生多文件包、安装命令、平台选择及升级恢复的支持尚未在本规范中验证。
2. SkillHub 如何分发纯规范包、以及规范与 Skill 的绑定方式，待实际验证后确定。
3. 包签名或构建来源证明的统一格式尚未规定；当前必须按 DEL-005 记录实际可信来源检查。
4. 不同应用的插件注册和加载机制由产品声明；本文不提供通用注册脚本。

上述事项不影响规范草稿的审阅。产品涉及未解决事项时，必须缩小交付声明或保持预发布状态。
