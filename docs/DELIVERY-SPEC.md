# 构建、发布与安装规范

规范版本：`1.0.0`；状态：`stable`；驱动结构版本：`2.0`；基线：ai-native-cli-spec `v1.6.3`。

本文面向 CLI、适配器和安装器的实现者，以及发布验收者。读者应了解 Git 版本、构建产物和文件校验，并已读过基线 REPO-SPEC 的版本、分发与 CHANGELOG 约定。
「必须」「不得」表示验收要求；「建议」表示可说明理由后采用其他方案。

## 目标与适用范围

本规范定义从源码版本到安装后实际运行版本的追溯关系，覆盖 CLI、适配器、加载进原应用的插件或服务，以及配套的 Skill。
产品按实际交付的组件和执行环境声明兼容性；文件工具、服务型会话和设备控制器适用同一追溯原则，不要求 GUI、某个品牌插件或特定文件格式。原应用进程加载、许可、驱动、宿主架构等要求仅在相关组件存在时适用；存在但未验收不能标为不适用。
产品包是具体工具的可安装产物；规范包是本规范的文本、Schema、基线副本和示例，两者分别发布。本文规定交付结果，不规定实现语言，也不要求所有工具采用同一种安装目录。
规范版本的状态表示公共契约是否通过规范准入；产品能力的成熟度和分发平台的支持另行验收。

## 发布场景

发布者从确定的源码提交构建平台包，生成 GitHub Release，再通过 SkillHub 分发（LAY-008）。
安装者（常常是 Agent）取得获授权的产物，检查来源与完整性，安装后核实 CLI 和实际运行的适配器版本。
升级可能同时涉及磁盘文件和原应用中已加载的服务；二者必须分别检查。

## 版本与产物

### DEL-001：发布入口与 Agent 安装路径

产品必须以 GitHub Release 记录版本化的产物，通过 SkillHub 分发；这项交付配置偏离基线的 npm 壳要求，理由见 LAY-008。必须满足：

- 至少一条验证过的 Agent 安装路径和一条升级路径，写在 README 的安装块和入口 Skill 中，可以复制执行；
- 各渠道交付的是同一套产物（DEL-003）；
- 私有 Release 的下载使用获授权的身份，安装脚本不得内嵌个人令牌；
- 某个渠道尚未验证时，不得写成已支持。

产品不能公开分发某些组件时（例如依赖许可的插件），必须说明哪些组件走哪条渠道，以及 Agent 如何取得它们。

验收：在干净环境中按 README 的安装块安装、按 Skill 的升级配方升级，都能得到声明的版本；未验证的渠道在文档中标为未验证。

### DEL-002：确定的源码版本

Release 必须对应不可变的源码提交，并记录 `source_commit`、构建环境和构建步骤。发布构建不得包含未提交的修改。标签名、包版本和 manifest 版本必须一致。
不得用移动标签、分支名或「最新版」代替已发布版本的身份。

验收：从标签重新构建能得到相同的组件清单和校验值，或说明不可复现的部分。

### DEL-003：产物一致性

各渠道交付的产品包必须与 Release 包逐字节一致，不得在上传前重新构建或修改内容。分发平台重新包装时，必须保留原包的校验值及包装关系，并验证安装后的组件内容一致。
内容发生变化时必须生成新版本，不得静默替换已有版本的产物，也不得用同一个版本号构建出内容不同的包。

验收：渠道上的包哈希与 Release 资产一致；同一版本号只对应一组组件哈希。

### DEL-004：manifest 内容

产品包必须携带符合 [Release manifest Schema](../schemas/release-manifest.schema.json) 的 manifest：规范版本、基线版本、产品版本、源码提交、目标系统与架构，以及组件路径、角色、版本和 SHA-256。
CLI、适配器、服务、插件、JAR、DLL 等实际交付的组件都必须逐项列出；不适用的组件不必虚构。

验收：manifest 的组件清单与包内文件一致。

### DEL-005：完整性与来源

供应链要求沿用基线 SEC-SPEC §5：发布产物附带 `checksums.txt`，由打标签的发布工作流用 Sigstore keyless 签名；带自更新的产品在进程内验签，失败关闭，返回不可重试的 `E_INTEGRITY`；分发涉及的每个生态都跑依赖审计，合并路径和发布路径都跑。
驱动层增加：加载进原应用进程的组件（插件、服务、DLL、JAR）与 CLI 一样纳入 checksums 和签名范围；安装或注册它们之前必须核对哈希。
组件 SHA-256 只证明内容一致，不证明发布者身份；只比较同一不可信来源提供的文件与哈希，不算来源验证。

验收：篡改任一组件后，安装或自更新以 `E_INTEGRITY` 失败；发布工作流在签名前完成审计。规范仓库的合并和标签路径都运行 `check_graduation --audit`，并对规范 ZIP、manifest 与验收材料生成 checksums.txt；标签工作流 keyless 签名后按精确仓库/workflow/tag 身份和 GitHub OIDC issuer 校验，失败不发布。外部消费者先验签再核实摘要；`verify_spec_bundle` 仍只证明内容完整性，不报告来源已认证。

### DEL-006：依赖与兼容范围

manifest 必须声明原应用、插件、协议和 Skill 的兼容范围，并记录安装所需的外部运行时。兼容声明必须说明版本范围、平台、架构及验证证据；未测试的组合必须标为未验证。
许可、驱动或应用安装等外部前提必须可以检查，不得宣称为产品包自带的能力。

验收：manifest 中每个 verified 的兼容项都有证据引用。

### DEL-007：平台包边界

每个包必须明确目标操作系统与架构，安装器必须在写入前检查目标是否匹配。不得把某个平台的构建成功外推为其他平台可安装或可运行。
涉及应用进程内加载时，必须检查宿主进程的架构；只检查操作系统架构不够。

验收：在不匹配的平台或宿主架构上安装时，写入前就被拒绝。

## 安装与升级

本节适用于把组件安装进原应用或系统位置的安装器（插件、服务、注册信息）。CLI 本身通过包管理器安装时，包管理器负责的部分按基线执行。

### DEL-008：先检查后写入

安装器必须先检查包的来源、哈希、目标路径、平台、依赖和目标目录现状，再修改安装文件。
包中路径必须解析到声明的安装根目录；绝对路径、路径穿越和越界链接必须拒绝。失败时必须说明是否已写入、已恢复或状态未知，不能以下载完成代表安装成功。

验收：带路径穿越的包在写入前被拒绝；失败的安装报告实际写入状态。

### DEL-009：保护已有内容

安装器只能替换其安装记录明确拥有的文件，必须保留用户配置、工程和其他软件的文件。发现未登记的同名文件时，必须报告冲突并停止覆盖，或使用独立的版本目录。
安装器不得递归清理未经核实的目录；卸载同样受文件归属约束。

验收：目标目录中预置的未登记同名文件在安装后原样保留。

### DEL-010：升级检查点

升级必须在切换前保留可恢复的旧版本与安装记录，并完整检查候选版本。多组件包必须作为同一版本集合切换，不能静默留下 CLI、插件和适配器的混合版本。
无法原子切换时，必须说明步骤、失败状态与恢复方法；不得假称事务回滚。

验收：升级中途失败后，组件版本要么全部是旧版本，要么报告混合状态和恢复方法。

### DEL-011：恢复结果

升级失败后，安装器必须验证恢复是否完成，并报告当前磁盘组件版本及应用中实际运行的版本。原应用的数据格式已经迁移时，不得假定恢复旧二进制即可恢复工程。
恢复不可执行或不可证明时，必须返回未知或需要处理的状态，并保留诊断信息。

验收：恢复后的报告区分磁盘版本与运行版本。

### DEL-012：应用集成边界

默认安装只完成包自身的部署，不得自动改变原应用的注册、全局插件配置、许可状态或重启原应用。需要这些动作时，必须作为带 `configure` 效果的危险命令单独提供，说明作用范围、前提及恢复方式，并要求任务范围允许。
部署完成、插件已注册、插件已加载和服务可连接必须分别报告。

验收：安装命令不修改原应用的注册；注册命令在 reference 中标为 dangerous。

### DEL-013：版本读回

安装后必须核实 CLI 版本、磁盘上的适配器版本，以及原应用中实际运行的插件或服务版本，并在 context 中分别报告（COR-009）。
运行中的服务必须提供构建身份或可核实的等效证据，不能只回显客户端期望的版本。服务尚未重载、无法读取身份或不兼容时，不得报告整套工具已就绪。

验收：服务未重载时 doctor 的 native_backend 检查失败并给出修复方法。

### DEL-014：诊断与可重试

安装器必须提供可以重复运行的版本与健康检查，重复检查不修改工程或应用配置。安装日志记录阶段、版本和恢复结果，屏蔽凭证及许可密钥。
重复安装已完成的同一版本时，应核验内容并给出明确结果；不得反复覆盖未知文件。

验收：连续两次运行健康检查，结果一致且没有写入。

## 渠道与 Skill

### DEL-015：分发阶段独立记录

构建、Release 上传、渠道上传（npm、SkillHub 等）、CLI 登记、Skill 绑定、版本发布和安装验证必须分别记录结果。某一步成功不代表后续步骤已成功；某个平台不存在某一步时，标明不适用和依据。
自动化凭证必须来自受控配置，不得随产品包或公开日志分发。

验收：发布记录逐步给出结果，失败的步骤不被后续成功掩盖。

### DEL-016：实际安装路径验证

发布者必须验证所用渠道的下载、安装、更新及版本查询能处理产品的实际文件结构。不得因为平台提供了某种登记选项，就推断它支持任意原生多文件包。
未验证的上传、登记或安装能力必须列为开放问题；解决之前不得宣称该渠道的完整链路可用。

验收：每个宣称可用的渠道都有一次实际安装与升级的记录。

### DEL-017：Skill 与 CLI 配套

Skill 遵循基线 SKILL-SPEC 和[驱动 Skill 增补](SKILL-ADDENDUM.md)：frontmatter 的 `version` 与 `metadata.requires.min_version` 等于工具版本，`metadata.requires.bins` 是工具的可执行文件名；Skill 的前置体检比较 `context.version` 与 `min_version`（基线 §14 的版本协商），不满足时停止并提示升级。
Skill 描述任务意图、适用条件和配方，参数及结果结构以运行时 reference 为准，不复制整份命令手册。
首次使用或版本变化后，调用方必须重新发现能力、检查环境与兼容性，并用 `changelog --since <旧版本>` 读取变化；有自更新的产品按基线 §14 同步全部 Skill。渠道的绑定记录不能代替运行时的兼容检查；发现不兼容时停止依赖该能力的操作。

验收：Skill 的版本字段与工具版本一致；升级后的配方先读 changelog 再继续。

### DEL-018：受控的可见范围

私有仓库和 Release 不自动保证渠道上产物的可见范围。发布者必须核实分发对象、下载权限与更新权限；凭证失效时不得静默切换到未经授权的镜像。
权限检查失败属于分发失败，不能用公开副本绕过。

验收：可见范围与发布计划一致，并有核对记录。

## 发布验收

### DEL-019：产品发布门禁

稳定的产品 Release 必须满足[验证规范](VERIFICATION-SPEC.md)中自己声明的能力、版本与环境范围，以及基线的发布就绪条件。
稳定版发布者必须从 Release 下载实际的包，验证安装、版本读回及声明能力的代表性真实操作。产品声明支持升级或恢复时，稳定发布前必须验证对应路径；不支持的路径必须明确声明。
只有源码测试通过或本地开发目录能运行，不足以证明发布包可用。

验收：稳定发布附有下载包的安装与真实操作证据。

### DEL-020：单一来源的发布记录

CHANGELOG 是变更记录的唯一来源（基线 REPO-SPEC §4）：Release 描述和运行时 `changelog` 命令都从它生成，不另外手写发布说明。
产品与独立组件各自指定唯一的版本来源；manifest、运行版本、Skill 版本及包元数据必须从该来源生成，或通过漂移校验。发布前必须核实清单中的组件版本与实际产物一致。
破坏性变化必须指出受影响的调用和迁移方法，不能只写「修复若干问题」。

验收：Release 描述与 CHANGELOG 对应版本段一致；版本漂移校验在 CI 中失败关闭。

### DEL-021：草稿与实验发布

`draft` 或 `experimental` 可以形成预发布 Release，允许未完成实测，但必须逐命令记录成熟度与限制。
未完成的检查、升级或恢复路径必须明确记录，不得借用稳定版的描述或宣称已通过验收。预发布仍必须保留来源追溯、包身份、目标平台、兼容范围和验证对象的声明。
稳定发布只覆盖已声明并完成验收的能力与环境，不代表支持所有应用版本。

验收：预发布的 reference 中 release_readiness 不是 stable。

### DEL-022：规范包

本规范自身的 Release ZIP 必须包含该版本的规范文本、基线副本及其锁定记录、驱动契约、Schema、示例、变更记录和校验入口，以及运行依赖说明。
规范包不得伪装成可执行的 CLI 产品，不得仅为分发规范而登记一个 CLI。规范包上传到其他平台时，必须验证适合文本规范的资源类型和读取方式；不支持时只保留 Release 交付。

验收：规范 ZIP 的组件清单包含完整正文、基线、contract、公共 Schema、SDK、种子与可执行例子；必需清单由消费端验证器定义，不能由包内 manifest 自行缩减；verify_spec_bundle 拒绝删去必需文件后仍哈希自洽的 ZIP。

### DEL-023：消费项目固定规范

消费项目必须固定驱动规范版本、驱动结构版本和基线标签，并记录本地副本的来源提交、规范包校验值及每个公共文件的校验值。
固定记录符合 [adoption-lock Schema](../schemas/adoption-lock.schema.json)，并写明副本取自哪里：规范包（`source_kind: bundle`，必须有包哈希和来源提交）、Git 检出（`git_checkout`，写明提交和是否有未提交的修改）或无版本的副本（`unversioned_copy`）。包和副本必须按记录的实际哈希校验，不能只比较自报版本。必须提供离线一致性检查，核实公共副本及生成物没有漂移；领域扩展与公共规范分开维护。
升级必须审阅规范差异，并重验受影响的能力；允许逐命令迁移，但必须明确未迁移的项、成熟度和限制。未迁移或未验证的项不得汇总成全工具已符合新版本。

验收：`scripts/check_adoption.py` 对取自规范包的固定记录和副本通过，改动任一副本后失败；种子工程的 `check_project.py` 对检出记录做同样的核对。

### DEL-024：独立版本与兼容变化

CLI 产品版本、组件协议版本、驱动结构版本、驱动规范版本和基线版本必须分别记录，不因其中一个变化自动改写其他版本。
CLI 产品沿用基线 [SemVer](https://semver.org/)。规范工作版本默认保持 1.0.0，驱动结构 2.0 独立记录不兼容变化；采用方必须核对结构、来源及哈希。正式发布不同内容时必须形成新版本和标签，例如 1.0.1，并清楚说明结构迁移；已发布版本不得对应另一份内容。
删除已支持的模式、命令或参数，改变默认值、状态含义、单位或恢复语义，都是破坏性变化。新增字段或枚举只在既有消费方仍可接受时才算兼容；通过 JSON 形状检查不能证明语义兼容。

验收：每个版本号只对应一组组件哈希；升级记录说明影响范围与迁移方法。

### DEL-025：规范发布门禁

规范 Release 必须满足[规范发布验证](VERIFICATION-SPEC.md#ver-024规范发布验证)，从确定的提交构建并验证本次规范包。
发布前必须重新消费 ZIP，核实文件清单、组件哈希、manifest、基线锁定、公共 Schema 及校验入口，不以构建命令成功代替。包校验必须拒绝路径穿越、重复或别名条目、链接与超限内容；内在一致性通过不得冒充独立的来源认证。
规范发布证明契约与交付包满足准入，不把任何具体产品提升为 stable，也不代替渠道的原生包安装实测。
包中的参考实现、开发模板与非规范性案例必须保留各自的证据范围，不能被规范的 stable 状态汇总成跨领域或跨工具的已支持结论。

验收：发布工作流在 STATUS 不是 stable 时拒绝发布；Release 描述取自 CHANGELOG。

## 异常与待定事项
