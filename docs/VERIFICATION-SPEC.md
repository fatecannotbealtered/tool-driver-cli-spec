# 契约、真实操作与产物验证规范

规范版本：`1.0.0`；状态：`stable`。

本文面向 CLI、适配器和验收实现者。读者应了解结构化接口、自动化测试和所驱动应用的基本操作。
「必须」「不得」表示验收要求；「建议」表示可说明理由后采用其他方案。

## 目标与适用范围

本规范定义如何证明一项能力在声明的版本和环境中符合契约，并取得预期状态或产物。
协议验证检查参数、结果和错误语义；真实操作验证检查原应用中的对象与状态；产物验证检查保存或导出的内容。
通过工具验证不等于取得工程签核、制造批准或设备运行许可，这些结论由对应领域流程决定。
规范自身的稳定准入、产品 CLI 的符合性和具体能力的真实验证，是分别取证的结论。

## 验证场景

实现者新增或修改能力，需证明调用成功、实际状态和交付内容之间的对应关系。
发布者需从发布包取得与源码测试一致的证据；使用者需知道当前环境是否落在验证范围内。
异常验证需区分未执行、已应用、部分应用、已恢复和无法确定，具体操作状态遵循 [核心规范](CORE-SPEC.md)。

## 声明与证据

### VER-001：按能力声明覆盖

验证声明必须按能力、应用版本、平台、适配器版本和工作模式记录，不得只给全局通过标记。
同一命令的只读、写入、保存、导出和恢复可以具有不同覆盖范围，必须分别说明。
README、Skill、reference、帮助及维护入口声明的公开行为，必须关联能力 ID、阶段、环境和适用条款。
已验证的每项行为必须可追溯到实际命令级测试运行报告及对应证据；报告需记录测试标识、实际调用、结果与来源版本。
扫描测试源码中的命令词或只报告代码覆盖百分比，不能证明该行为已执行并通过验收。
未测、无法测试和不支持必须区分，不能全部省略成「未发现问题」。

### VER-002：成熟度不替代结果

每项能力必须标明 `draft`、`experimental`、`verified` 或 `stable` 及适用环境；成熟度不替代测试记录。
`draft` 只代表契约可审阅；`experimental` 必须列出限制；`verified` 或 `stable` 必须有对应环境证据。
不得根据命令数量、Schema 验证通过或整个仓库的状态，推断单项能力已具备生产可靠性。

### VER-003：检查状态

每项检查必须使用 `not_run`、`passed`、`failed`、`incomplete` 或 `not_applicable`，并说明证据入口。
结果未知或证据不完整必须用 `incomplete` 并解释未核实项；未执行必须用 `not_run`。
`not_applicable` 必须有适用条件依据；缺少应用、许可、样本或判定器不能当作不适用。
只完成部分检查时，不得聚合为全部验证通过；覆盖率必须说明分母与排除范围。

### VER-004：证据绑定

证据必须符合 [验证证据 Schema](../schemas/evidence.schema.json)，声明 `evidence_context` 为 `development` 或 `release`。
`development` 未形成产品包时允许 `package_sha256` 为 `null`，但必须记录源码与构建身份，并在 `limitations` 中标明未覆盖发布包。
`release` 必须绑定实际下载包的 SHA-256、源码提交和实际组件版本，不得以开发构建证据替代。
证据必须记录适用的原应用与服务构建身份，区分客户端版本、磁盘版本和实际运行版本。
还必须记录目标实例、文档版本、输入与依赖指纹、时间、命令、关键结果和验证方法。
无法读取某项哈希或身份时必须说明替代证据与局限，不能填入客户端期望值冒充实际读回。

### VER-005：证据可复核

证据必须允许验收者定位输入、执行过程和结果；日志截图不得代替全部结构化状态。
涉及私有工程时可使用受控样本，但必须说明其代表范围。脱敏不得删除判定必要的依赖或数值。
凭证、许可密钥和个人令牌不得进入证据包。

## 协议契约验证

### VER-006：机器契约

契约验证必须覆盖参数约束、结果 Schema、默认 JSON、UTF-8 编解码、退出码、错误分类、能力发现和版本协商。
必须验证未知参数、类型错误、范围越界、缺少前提及不支持能力的结果。
reference 守卫必须枚举每项能力，实际解析其 `request_schema` 和 `result_schema`，并确认引用可定位。
守卫必须检查每项能力提供合法示例 argv，且与命令路径、必需参数及类型约束一致；不得自动执行示例。
命令级测试必须运行 CLI 边界并检查实际结果，不能只验证内部函数或 reference 的字段存在。
契约通过只能证明 CLI 边界符合声明，不能证明原应用已经完成操作。

### VER-007：副作用边界

只读能力必须验证不会改变工程、保存状态或应用配置；预览必须验证声明的副作用范围。
写入能力必须验证授权范围、目标身份和前置状态检查发生在首次修改之前。
超出范围、状态已变化或目标不明时，必须验证没有对错误对象继续执行。

### VER-008：模拟环境

模拟器、桩服务和录制响应只能证明覆盖到的 CLI 协议行为。
模拟测试必须显式标记；不得作为插件真实加载、应用修改、持久化或产物正确的证据。
原应用暂不可用时可以完成协议验证，但真实能力的成熟度不得随之提升。

## 真实操作与读回

### VER-009：真实实例

运行实例模式必须连接真实应用或设备，并核实实例、会话、文档与对象身份。
文件模式必须使用真实产物，由原应用重新加载或声明的独立消费者检查，不能以模拟响应代替。
测试必须使用受控对象并记录实际版本与依赖配置；文件修改和运行实例修改必须分开验证。

### VER-010：应用后读回

每类写入必须从原应用或独立解析后的文件读回受影响对象与不变量。
返回成功、对象 ID 或提交回执不等于验证完成。读回必须检查实际属性、关系与状态。
读回失败时必须保留操作已发生的可能性，不得把验证失败改写成未执行。

### VER-011：独立判定

关键能力必须增加不与实现共用同一缺陷来源的判定方法，如原应用检查器、独立解析器或已知样本。
仅用同一个错误计算结果生成期望值再自我比较，不算独立验证。
判定器之间有差异时必须记录对象、条件及差异，不得隐藏不一致或擅自决定谁正确。

### VER-012：视觉与交互结果

布局、图纸、视图或其他依赖呈现的能力必须在原应用或声明的渲染路径检查实际输出。
图片证据必须记录渲染条件、关键视角及验收点；单张截图不能证明连接、几何或内部关系完整正确。
视觉检查与结构检查必须各自保留结果，不能互相替代。

### VER-013：持久化与往返

声称已保存的能力必须核实磁盘产物，并在关闭后重新打开，或使用等效独立加载方式检查。
导出与导入能力必须验证格式、单位、关系和声明保留的信息，不只检查文件存在或大小非零。
多文件交付必须绑定同一工程版本和依赖集合；重新打开时悄悄切换库或参考文件属于验证失败。

## 异常与依赖验证

### VER-014：状态与依赖漂移

必须验证预览后文档修改、实例切换、外部文件变化、库变化和对象失效的处理。
证据必须表明工具在执行前核实哪些前提，以及哪些变化会使操作失效。
身份相同但内容已变时，不得继续用旧预览或旧对象引用执行。

### VER-015：失去回复

必须覆盖超时、连接断开、服务崩溃及 CLI 终止后操作可能仍在运行的场景。
首次回复丢失时，必须验证调用方能用提交前已知的请求或操作标识查询状态或回执，不能依赖丢失回复中的 ID。
查询索引和回执保留期限必须声明；记录过期或查无结果不能被判为未执行。
无法判定是否应用时，必须验证工具报告未知，并提供状态查询或核实路径。
非幂等操作不得在未知状态下自动重发；必须验证重复请求不会误造成第二次修改。

### VER-016：部分应用与恢复

多步写入必须在修改前、部分应用、保存期间和恢复期间设置故障场景。
验证必须明确哪些对象已变、哪些文件已保存、哪些后续步骤未执行，以及恢复是否读回成功。
备份存在或恢复命令返回成功，不足以证明已恢复；仍有残留时必须报告。

### VER-017：批量与依赖

独立批量必须验证逐项结果和整体结果；有依赖的步骤必须验证停止、跳过及恢复条件。
上游失败后，依赖该结果的步骤不得继续使用缺失或旧对象。
仅存在部分成功时，汇总必须保留部分应用事实，不能用批次已处理掩盖失败。

### VER-018：单位与坐标

涉及量纲或几何的能力必须验证单位转换、精度、坐标系、原点、方向及变换顺序。
至少覆盖声明的边界值、非默认单位、嵌套或局部坐标，以及超出合法范围的输入。
无单位或参考系不明的参数必须按契约拒绝或明确默认值，不能靠界面习惯推断。

### VER-019：并发与取消

必须验证多个调用及人工编辑并发时的冲突检测、排队或拒绝行为。
使用锁或租约时必须覆盖其失效但原生操作仍在运行的场景，后续写入不得只凭锁到期进入。
必须验证模态窗口、忙碌主线程和不可中断原生调用的有限等待；超时报告实际已知阶段及未知结果。
取消必须验证实际停止点及已发生的修改；发出取消请求不等于操作已停止或已回滚。
长操作取消后若后台仍在运行，必须报告该状态并禁止不安全的后续写入。

### VER-020：不变量与保护对象

每类操作必须明确预期变化及应保持的对象或约束，并验证两者。
测试必须检查相关对象、依赖和用户已有内容，不能只验证新对象存在。
无法全面检查时必须列出未覆盖的不变量，避免宣称无副作用。

## 发布验收

### VER-021：实际包与实际服务

CLI 产品发布验收必须运行实际下载的产品包，确认原应用连接的是该版本服务，而非开发目录的旧服务。
有独立更新组件时必须覆盖兼容组合和不兼容组合；无法读取服务版本时不得默认匹配。
源码提交、包哈希或服务版本变化后，不能直接沿用旧证据作新版本通过结论。

### VER-022：与声明相符的门禁

稳定 CLI 产品发布必须满足所有声明支持能力在其声明环境中的契约与真实验收要求。
出现失败或未知时必须修复、缩小支持范围或保持预发布，并披露原因。
对明确不支持的环境无需假装验收，但必须验证其识别与拒绝行为。
草稿或实验预发布允许验证未完成，但必须按 [草稿与实验发布规则](DELIVERY-SPEC.md#del-021草稿与实验发布) 保留成熟度、限制和身份声明。

### VER-023：维护验证范围

变更需重跑受影响的契约、真实操作、持久化与恢复检查；应用或依赖升级需重验受影响能力。
未变化且可证明不受影响的证据可以引用，必须保留引用版本和影响判断。
验收记录应保留已知差异、未执行场景和排除理由，不能只保存成功截图。

### VER-024：规范发布验证

规范 stable 准入必须完成文本与公共机器契约的一致性检查、可解析正反例和有意义的静态及边界测试。
测试必须覆盖声明解析、公共错误和字段约束、状态关系，以及查询、任务和组合操作的适用公共结构。
至少完成一种真实文件产物的独立消费试验，保留执行环境、来源、产物校验值与实际消费结果；静态样例或模拟响应不能替代。
本次规范包必须重新加载校验；有缺失文件、校验值不符或公共契约冲突时不得发布稳定规范版本。
上述准入只证明规范与本包在声明范围内可实施，不证明所有运行实例、设备、领域检查或分发平台已通过验收。

### VER-025：产品 CLI 符合性

公共符合性入口必须能离线解析产品 reference，检查公共错误、参数绑定、字段类型、示例请求和公共结果结构。
静态检查不得自动执行 reference 示例，也不能证明 argv 到请求的实际映射、真实退出码或原生副作用。
产品必须另以实际 CLI 边界测试验证这些行为，并将测试运行报告关联能力、阶段、适用条款及环境。
公共副本检查需核实受控固定记录、规范包内容和采用的文件字节；自报版本相同不能替代内容与路径检查。
模拟适配器只能支持所测协议结论；文件消费者、运行应用和设备的证据必须按实际模式分别记录。
允许逐能力实施，未完成检查明确标记并限制成熟度；不得以公共校验通过代替产品 stable 准入。

## 开放问题与边界

1. 各领域的独立判定器、代表性样本和工程不变量由能力声明补充，不设通用工程正确性分数。
2. 证据 Schema 规定最小记录；不同领域的自动判定器及证据聚合策略尚待具体能力定义。
3. 设备带来的人身、物理或不可逆动作风险，需对应领域规则；软件仿真证据不代表设备实测。

具体产品的生产成熟度必须依据它自身的验证声明与证据判定，不从规范版本状态继承。
