# 契约、真实操作与产物验证规范

规范版本：`1.0.0`；状态：`stable`；驱动结构版本：`2.0`；基线：ai-native-cli-spec `v1.6.3`。

本文面向 CLI、适配器和验收的实现者。读者应了解结构化接口、自动化测试和所驱动应用的基本操作，并已读过基线 CLI-SPEC §13（功能契约覆盖率与发布就绪）。
「必须」「不得」表示验收要求；「建议」表示可说明理由后采用其他方案。

## 目标与适用范围

本规范定义如何证明一项能力在声明的版本和环境中符合契约，并取得预期的状态或产物。
协议验证检查参数、结果和错误语义；真实操作验证检查原应用中的对象与状态；产物验证检查保存或导出的内容。
通过工具验证不等于取得工程签核、制造批准或设备运行许可，这些结论由对应的领域流程决定。
规范自身的准入、产品 CLI 的符合性和具体能力的真实验证，是分别取证的结论。

## 验证场景

实现者新增或修改能力，需要证明调用成功、实际状态和交付内容之间的对应关系。
发布者需要从发布包取得与源码测试一致的证据；使用者需要知道当前环境是否落在验证范围内。
异常验证需要区分未执行、已应用、部分应用、已恢复和无法确定，具体状态遵循[核心协议](CORE-SPEC.md)。

## 声明与证据

### VER-001：按能力声明覆盖

基线的功能契约覆盖率（FCC）门禁原样适用：README、Skill、reference、帮助、context、doctor、changelog、update 中声明的每个公开行为都要有命令级测试。
驱动层增加：每条命令的覆盖按能力、应用版本、平台、适配器版本和驱动模式记录；同一命令的只读、写入、保存、导出、交付和恢复可以有不同的覆盖范围，必须分别说明。
已验证的行为必须能追溯到实际的命令级测试运行报告及对应证据，报告记录测试标识、实际调用、结果与来源版本。扫描测试源码中的命令词，或只报告代码覆盖百分比，不能证明行为已执行并通过。
未测、无法测试和不支持必须区分，不能全部省略成「未发现问题」。

验收：枚举 reference 的每条命令，都能找到调用它的命令级测试；FCC 守卫在缺少测试时失败。

### VER-002：成熟度不替代结果

每条命令的 `driver.maturity` 标明 `draft`、`experimental`、`verified` 或 `stable` 及适用环境；成熟度不替代测试记录。
`draft` 只代表契约可以审阅；`experimental` 必须列出限制；`verified` 或 `stable` 必须有对应环境的证据（`evidence_refs`）。
工具级的 `release_readiness` 按基线判断，并受逐命令成熟度约束：`stable` 发布不得暴露 `draft` 命令。不得根据命令数量、Schema 校验通过或整个仓库的状态，推断单项能力具备生产可靠性。

验收：reference 中 verified 或 stable 的命令都有证据引用；stable 的 reference 没有 draft 命令。

### VER-003：检查状态

每项检查使用 `not_run`、`passed`、`failed`、`incomplete` 或 `not_applicable`，并说明证据入口。
结果未知或证据不完整用 `incomplete` 并说明未核实的项；未执行用 `not_run`。`not_applicable` 必须有适用条件依据；缺少应用、许可、样本或判定器不能当作不适用。
只完成部分检查时，不得聚合为全部通过；覆盖率必须说明分母与排除范围。

验收：部分检查的结果不会被汇总成 passed；not_applicable 都有依据。

### VER-004：证据绑定

证据必须符合 [evidence Schema](../schemas/evidence.schema.json)，声明 `evidence_context` 为 `development` 或 `release`。
`development` 未形成产品包时允许 `package_sha256` 为 null，但必须记录源码与构建身份，并在 `limitations` 中写明未覆盖发布包。`release` 必须绑定实际下载包的 SHA-256、源码提交和实际组件版本，不得以开发构建的证据替代。
证据必须记录原应用与服务的构建身份，区分客户端版本、磁盘版本和实际运行版本；还要记录目标实例、文档版本、输入与依赖的指纹、时间、实际命令、关键结果和验证方法。无法读取某项哈希或身份时，必须说明替代证据与局限，不能填入客户端的期望值冒充读回。

验收：每份证据都能对上一个源码提交、一组组件身份和一组实际命令。

### VER-005：证据可复核

证据必须让验收者能定位输入、执行过程和结果；日志截图不得代替全部结构化状态。
涉及私有工程时可以使用受控样本，但必须说明代表范围。脱敏不得删除判定必要的依赖或数值。凭证、许可密钥和个人令牌不得进入证据包。

验收：另一位验收者按证据能重放调用或复核结论。

## 协议契约验证

### VER-006：机器契约

契约验证必须同时覆盖基线与驱动层：

- 基线：信封键集合、核心错误码与退出码、retryable、自描述命令的必含键、分页与批量结构、`_untrusted`，按基线 contract.json 的运行时一致性测试；
- 驱动层：reference 的 driver 块、驱动扩展错误码、错误 details 的必含键、回执推导的错误码（COR-003）、计划与令牌、操作记录命令。

必须验证未知参数、类型错误、范围越界、缺少前提、缺少确认令牌、缺少 `--dangerous`、缺少授权范围及不支持能力的结果，并检查 `details.problem` 与 `next_action`。
reference 守卫必须枚举每条命令，确认 schemas 条目、错误引用、示例和 driver 块可离线核对；守卫不得自动执行示例。
命令级测试必须运行 CLI 边界并检查实际结果，不能只验证内部函数或 reference 的字段存在。契约通过只能证明 CLI 边界符合声明，不能证明原应用已完成操作。

验收：`scripts/validate_contract.py` 对产品的实际输出通过；每条命令的失败路径都有命令级测试。

### VER-007：副作用边界

只读能力必须验证不会改变工程、保存状态或应用配置；预览必须验证声明的副作用范围。
写入能力必须验证授权范围、目标身份和前置状态检查都发生在首次修改之前。超出范围、状态已变化或目标不明时，必须验证没有对错误对象继续执行。

验收：缺少授权和状态漂移的测试中，原生适配器没有收到写调用。

### VER-008：模拟环境

模拟器、桩服务和录制的响应只能证明覆盖到的 CLI 协议行为。模拟测试必须显式标记；不得作为插件真实加载、应用修改、持久化或产物正确的证据。
原应用暂不可用时可以完成协议验证，但真实能力的成熟度不得随之提升。

验收：模拟证据的 kind 为 `simulated_adapter`，相关命令的成熟度不超过 experimental。

## 真实操作与读回

### VER-009：真实实例

运行实例模式必须连接真实应用或设备，并核实实例、会话、文档与对象身份。
文件模式必须使用真实产物，由原应用重新加载或由声明的独立消费者检查，不能以模拟响应代替。测试必须使用受控对象并记录实际版本与依赖配置；文件修改和运行实例修改必须分开验证。

验收：真实操作证据记录了实例或文件身份与实际版本。

### VER-010：应用后读回

每类写入都必须从原应用或独立解析后的文件读回受影响的对象与不变量。
返回成功、对象 ID 或提交回执不等于验证完成；读回必须检查实际属性、关系与状态。读回失败时必须保留操作已发生的可能性，不得把验证失败改写成未执行。

验收：读回失败的测试得到 `E_VERIFY_INCOMPLETE` 或 `E_OUTCOME_UNKNOWN`，不是未执行。

### VER-011：独立判定

关键能力必须增加不与实现共用同一缺陷来源的判定方法，如原应用的检查器、独立解析器或已知样本。
用同一个错误的计算结果生成期望值再自我比较，不算独立验证。判定器之间有差异时，必须记录对象、条件及差异，不得隐藏不一致或擅自决定谁正确。

验收：关键能力的证据至少含一项独立判定。

### VER-012：视觉与交互结果

布局、图纸、视图等依赖呈现的能力，必须在原应用或声明的渲染路径检查实际输出。
图片证据必须记录渲染条件、关键视角及验收点；单张截图不能证明连接、几何或内部关系完整正确。视觉检查与结构检查各自保留结果，不能互相替代。

验收：视觉证据与结构证据分开记录。

### VER-013：持久化与往返

声称已保存的能力必须核实磁盘产物，并在关闭后重新打开，或使用等效的独立加载方式检查。
导出与导入能力必须验证格式、单位、关系和声明保留的信息，不只检查文件存在或大小非零。多文件交付必须绑定同一工程版本和依赖集合；重新打开时悄悄切换库或参考文件属于验证失败。

验收：保存的证据包含重新加载后的读回。

## 异常与依赖验证

### VER-014：状态与依赖漂移

必须验证预览后文档修改、实例切换、外部文件变化、库变化和对象失效的处理。证据必须表明工具在执行前核实了哪些前提，以及哪些变化会使操作失效。
身份相同但内容已变时，不得继续用旧预览或旧对象引用执行。

验收：漂移测试得到 `E_CONFLICT`（`state_drift`），且没有派发。

### VER-015：失去回复

必须覆盖超时、连接断开、服务崩溃及 CLI 终止后操作可能仍在运行的场景。
首次回复丢失时，必须验证调用方能用 dry-run 时已知的 `operation_id` 查询状态或回执，不依赖丢失回复中的 ID。查询索引和回执保留期限必须声明；记录过期或查无结果不能判为未执行。
无法判定是否应用时，必须验证工具报告未知并提供查询或核实路径；同一目标的后续写入在登记前被拒绝。非幂等操作不得在未知状态下自动重发。
CLI 在执行中被终止时，必须验证记录在声明的租约期限后改报 unknown，期间同一目标的写入报 `lock_held`、登记被拒绝（DRV-035、DRV-041）。

验收：丢失回复的测试先得到 `E_OUTCOME_UNKNOWN`，再经 `operation show`、读回、`operation resolve` 恢复写入；终止 CLI 进程的测试中，记录不会一直停在 running。

### VER-016：部分应用与恢复

多步写入必须在修改前、部分应用、保存期间和恢复期间设置故障场景。验证必须明确哪些对象已变、哪些文件已保存、哪些后续步骤未执行，以及恢复是否读回成功。
备份存在或恢复命令返回成功，不足以证明已恢复；仍有残留时必须报告。

验收：每个故障点的回执和错误码与 COR-003 的推导一致。

### VER-017：批量与依赖

独立批量必须验证逐项结果和汇总；有依赖的步骤必须验证停止、跳过和恢复条件。
上游失败后，依赖该结果的步骤不得继续使用缺失或旧的对象。只有部分成功时，汇总必须保留部分应用的事实，不能用「批次已处理」掩盖失败。

验收：批量汇总与逐项结果一致；依赖步骤在上游失败后为 skipped 并说明原因。

### VER-018：单位与坐标

涉及量纲或几何的能力必须验证单位转换、精度、坐标系、原点、方向及变换顺序。
至少覆盖声明的边界值、非默认单位、嵌套或局部坐标，以及超出合法范围的输入。无单位或参考系不明的参数必须按契约拒绝，或使用明确声明的默认值，不能靠界面习惯推断。

验收：单位测试覆盖默认单位、非默认单位和不支持的单位。

### VER-019：并发、阻塞与取消

必须验证多个调用及人工编辑并发时的冲突检测、排队或拒绝行为。使用锁或租约时，必须覆盖锁已失效但原生操作仍在运行的场景，后续写入不得只凭锁到期进入。
必须验证模态窗口、忙碌的主线程和不可中断的原生调用都在有限时间内返回：模态窗口为 `E_HUMAN_REQUIRED`，忙碌且未派发为 `E_BUSY`，超时而已派发为 `E_OUTCOME_UNKNOWN`。
取消必须验证实际的停止点及已发生的修改；发出取消请求不等于操作已停止或已回滚。长操作取消后若后台仍在运行，必须报告该状态并禁止不安全的后续写入。

验收：每种阻塞都在声明的时限内返回对应错误码，不擅自确认对话框。

### VER-020：不变量与保护对象

每类操作必须明确预期变化及应保持的对象或约束，并验证两者。测试必须检查相关对象、依赖和用户已有内容，不能只验证新对象存在。
无法全面检查时必须列出未覆盖的不变量，避免宣称无副作用。

验收：写入测试同时断言变化与保持不变的对象。

## 发布验收

### VER-021：实际包与实际服务

CLI 产品发布验收必须运行实际下载的产品包，确认原应用连接的是该版本的服务，而不是开发目录里的旧服务。
有独立更新的组件时，必须覆盖兼容组合和不兼容组合；无法读取服务版本时不得默认匹配。源码提交、包哈希或服务版本变化后，不能沿用旧证据作为新版本的通过结论。

验收：发布证据的 package_sha256 与 Release 资产一致，context 读回的运行服务版本与包内版本一致。

### VER-022：与声明相符的门禁

稳定的 CLI 产品发布必须满足基线的发布就绪条件（FCC 100%、模拟上游的失败路径测试、真实环境 smoke 记录），并满足所有声明支持的命令在其声明环境中的契约与真实验收。
出现失败或未知时，必须修复、缩小支持范围或保持预发布，并披露原因。对明确不支持的环境无需假装验收，但必须验证识别与拒绝行为。
草稿或实验预发布允许验证未完成，但必须按[草稿与实验发布规则](DELIVERY-SPEC.md#del-021草稿与实验发布)保留成熟度、限制和身份声明。

验收：reference 的 release_readiness 与 doctor 的 release_readiness 检查一致，并与证据相符。

### VER-023：维护验证范围

变更需要重跑受影响的契约、真实操作、持久化与恢复检查；应用或依赖升级需要重验受影响的能力；基线版本升级需要重跑基线一致性测试。
未变化且可证明不受影响的证据可以引用，必须保留被引用的版本和影响判断。验收记录应保留已知差异、未执行的场景和排除理由，不能只保存成功截图。

验收：升级记录列出重跑的检查和引用的旧证据。

### VER-024：规范发布验证

规范准入必须完成：文本与公共机器契约的一致性检查；可解析的正反例和有意义的静态及边界测试；基线文件与锁定记录逐字节一致；驱动扩展码符合基线扩展规则。
测试必须覆盖声明解析、公共错误和字段约束、回执推导的错误码、状态关系，以及批量、查询、任务和组合操作的公共结构。
稳定版本还必须至少完成一种真实文件产物的独立消费试验，保留执行环境、来源、产物校验值与实际消费结果；静态样例或模拟响应不能替代。
本次规范包必须重新加载校验；有缺失文件、校验值不符或公共契约冲突时不得发布。上述准入只证明规范与本包在声明范围内可实施，不证明所有运行实例、设备、领域检查或分发平台已通过验收。

验收：`scripts/check_spec.py`、单元测试和 `scripts/verify_spec_bundle.py` 都通过；稳定版本附有独立消费证据。可用 `scripts/check_graduation.py` 执行并保留实际日志与源文件哈希；提供规范 ZIP 时必须运行包内检查和独立消费。具体命令与边界见 [工程任务验收](ENGINEERING-ACCEPTANCE.md)。

### VER-025：产品 CLI 符合性

公共符合性入口（`scripts/validate_contract.py`）必须能离线检查产品的 reference、context、doctor、changelog 输出和响应信封，包括基线必含键、错误码表、driver 块与公共结构。
静态检查不得自动执行 reference 示例，也不能证明参数解析、真实退出码或原生副作用；产品必须另以实际 CLI 边界测试验证，并把测试运行报告关联到命令、阶段、适用条款及环境。
公共副本检查需要核实受控的固定记录、规范包内容和采用的文件字节；自报版本相同不能替代内容与路径检查。模拟适配器只能支持所测的协议结论；文件消费者、运行应用和设备的证据按实际模式分别记录。
允许逐命令实施，未完成的检查明确标记并限制成熟度；公共校验通过不能代替产品的 stable 准入。

验收：产品 CI 对实际 CLI 输出运行 validate_contract，并检查固定副本无漂移。

### VER-026：Skill 评测

驱动 Skill 按基线 SKILL-SPEC §9 评测，并至少覆盖[驱动 Skill 增补](SKILL-ADDENDUM.md)要求的场景：缺少授权范围时停下请人授予、未请求保存时不保存、回复丢失后查询而不重发、多实例时不靠窗口焦点、对象备注中的指令不执行、模态框出现时转交给人。
评测必须记录调用轨迹、判定结果和模型与环境；提示文件存在或场景文字不代表 Agent 已通过评测。

验收：每个必选场景都有一次记录在案的评测运行。记录符合 [agent-eval Schema](../schemas/agent-eval.schema.json)，离线入口 `scripts/check_agent_eval.py` 检查来源文件、Skill、场景、模型版本、真实 argv/退出码/stdout/stderr、轨迹与结果证据的哈希及对应关系。发布评测还须包含至少三个无 Skill 基线场景与多个模型的全场景运行；模拟或 fixture 记录不能满足门禁。

此记录守卫不认证录制者、不代替独立判定工程结果；A/B 真实使用与导航观察按基线 SKILL-SPEC §9 执行并保留。软件正文列 Haiku/Sonnet/Opus 作为能力档示例；驱动记录不绑定供应商，机器最低门禁选两个不同模型身份，建议覆盖不同能力档。规范自身的协议回归不冒充产品的 Agent eval。

`evaluation_scope` 必须保留 SKL-010 的八类强制要求，分别声明 `supported`、`unsupported` 或 `not_evaluated` 并提供范围依据；未运行与不支持不得混为一谈。场景通过 `requirements` 关联稳定的要求标识，不能只靠场景数量宣称完整符合。
完整 `full_driver_skill` 门禁要求八类都声明支持、都进入评测集并被每个模型真实运行通过；缺少能力、样本或模型运行不能删除义务或改成豁免。受限的真实文件试验声明 `capability_subset`，可用 `--require-subset-pass` 验证其多模型覆盖，但该结果始终不能满足完整 Skill 或发布门禁。
隔离输入、真实工具录制与独立文件判定方法见 [Agent 评测执行](AGENT-EVAL-RUNBOOK.md)。

## 开放问题与边界

1. 各领域的独立判定器、代表性样本和工程不变量由能力声明补充，不设通用的工程正确性分数。
2. 证据 Schema 只规定最小记录；不同领域的自动判定器及证据聚合策略留待具体能力定义。
3. 设备带来的人身、物理或不可逆风险需要对应的领域规则；软件仿真证据不代表设备实测。

具体产品的生产成熟度必须依据它自己的验证声明与证据判定，不从规范版本的状态继承。
