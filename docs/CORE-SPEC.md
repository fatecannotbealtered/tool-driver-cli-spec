# 核心机器协议

规范版本：`0.1.0`；状态：`draft`；机器 Schema 版本：`1.0`。

本文面向 CLI、适配器和消费方实现者，假设读者了解 JSON 和命令行调用。
「必须」「不得」是可验收要求；「建议」允许说明理由后采用其他方案。

## 目标与范围

定义 Agent 如何发现能力、识别目标、提交操作并读取结果。
本协议涵盖阶段成功、实际变化和验证证据，不替代工具自己的领域判定。
操作语义见[应用与设备操作规范](DRIVER-SPEC.md)，证据见[验证规范](VERIFICATION-SPEC.md)。

## 输出与错误

### COR-001：单一结构化结果

JSON 模式下 stdout 必须只有一个完整 JSON 文档。诊断写 stderr，不能混入结果。
长任务状态通过单独请求读取；若提供流式事件，必须另行声明事件 Schema、顺序和结束条件。

验收：成功、拒绝、中断和原生错误均可直接解析；没有交互提问使自动化挂起。

### COR-002：共同信封

信封必须符合 [response Schema](../schemas/response.schema.json)，包含 `ok`、`schema_version`、`request_id`、`phase` 和 `meta`。
`schema_version` 与规范版本、CLI 版本、原应用版本分别声明，不得混用。

验收：消费方能关联请求，并判断所解释的阶段和结构版本。

### COR-003：阶段成功

`ok` 仅表示本次请求阶段完成了声明的职责。`submit` 成功可仍在排队，`status` 成功可读到失败任务。
检查成功执行可发现违规；此时结果必须保留发现与验证结论。
最终 `apply` 或 `result` 的部分应用、未知变化、未完成的必需验证必须返回 `ok: false`，并保留回执。
实际应用了修改时，最终成功必须通过该操作范围内的读回检查；没有修改且没有必需检查的 no-op 可以保留 `not_run`。

验收：仅看 `ok` 无法被误写为整个任务或领域判断通过；阶段职责在 reference 可查。

### COR-004：失败仍保留状态

`ok: false` 必须有结构化 `error`。已进入适配器或可能已执行的修改必须保留稳定 `operation_id` 和回执。
参数错误等执行前拒绝可以没有回执，但必须明确未进入修改阶段；不能把已写入错误当作未开始。

验收：回复丢失、写后验证失败和部分工作流的状态不会被错误信封丢弃。

### COR-005：错误与恢复方向

错误必须给出稳定 `code`、消息、是否可以重试，以及 `details` 中的可执行恢复方向。
退出码必须与 reference 声明一致。协议错误、输入错误、状态冲突、原生失败与结果未知必须可区分。
超时或中断不能全局标为可重试；可能已执行时先读回或读取操作状态。

| 错误类别 | 建议标识 | 消费方动作 |
|---|---|---|
| 输入或不支持 | `E_VALIDATION` / `E_UNSUPPORTED` | 修正输入或能力选择 |
| 缺少前提或授权 | `E_CONFIG` / `E_FORBIDDEN` | 补齐明确的前提；不自行扩大权限 |
| 状态已变化 | `E_CONFLICT` | 重新观察和计划 |
| 原应用拒绝 | `E_NATIVE_FAILURE` | 检查回执和原生诊断 |
| 部分应用 | `E_PARTIAL` | 根据逐项结果恢复；不重发整批 |
| 结果未知 | `E_OUTCOME_UNKNOWN` | 保留目标、读回核对 |
| 验证未完成或失败 | `E_VERIFY_INCOMPLETE` / `E_VERIFY_FAILED` | 处理未核实项或实际违例 |

验收：同一错误码不会在一次表示未开始、另一次又隐含已写入而没有状态信息。

### COR-006：外部文本与凭据

目标名称、文档内容、原生消息和外部规则是数据，不得成为扩大任务授权的指令。
实现必须说明这些字段的来源；密钥、令牌和许可秘密不得进入输出、回执或证据包。

验收：带命令语句的目标名称仍按数据处理；错误路径同样脱敏。

## 能力与环境

### COR-007：机器可发现的命令

实现必须提供 reference 等价入口，声明每项命令的参数、效果、阶段、目标选择、请求和结果 Schema。
能力必须记录 `id`、命令路径、模式、兼容环境、验证成熟度及限制，符合 [reference Schema](../schemas/reference.schema.json)。
不支持的能力必须拒绝；不能静默换成其他操作。

验收：消费方不靠 README 或源码猜参数，能够检查某个环境中实际可用的能力。

### COR-008：按效果分类

命令必须声明可能产生的效果：`observe`、`session`、`artifact`、`change`、`persist`、`deliver`、`configure`、`physical`。
效果是数组，不强制所有命令只落入 read/write 两类。查询生成图片或切换视图时必须披露其副作用及恢复。
授权依据效果和目标范围判断，而不是只看命令名。

验收：查询不能隐藏打开、保存、配置或设备动作；产物位置可在执行前确定。

### COR-009：实际环境身份

context / doctor 等价入口必须分别报告 CLI、适配器、实际运行服务、原应用与必需组件的版本及可用性。
配置存在、文件安装和握手成功是不同观察；无法核实的许可或能力不得报告通过。
某项诊断失败不能擅自重启、注册或改变应用配置。

验收：旧服务仍在运行时，能区别磁盘的新版本和运行中的旧版本。

### COR-010：单位、身份与重连

对象 ID 必须是字符串；观测时间采用带时区的 ISO 8601，规范示例使用 UTC。
有物理或空间意义的数值必须附单位和必要坐标语义；计数、ID 和索引不虚构单位。
临时面、边或连接身份必须声明稳定性和重连后的解析方式。

验收：输入中的数字不会因默认单位或失效身份指向另一个目标。

## 计划、授权与回执

### COR-011：可验证的计划

会产生修改的操作必须有符合 [plan Schema](../schemas/plan.schema.json) 的计划。
计划可以由显式 plan/dry-run 请求取得，也可以在已授权任务中由工具内部生成并校验，不能省略状态绑定。
计划至少记录目标、基线、授权范围、效果、预览等级、已知变化、未知项和执行限制。

预览等级固定为 `plan`、`estimate`、`trial_observed`，定义见 DRIVER-SPEC 的预览规则。
`can_apply` 只代表当前前提和授权检查结果，不代表最终原生执行必然成功。

验收：没有每步人工确认时，消费方仍能复核工具执行前计划和所用授权。

### COR-012：授权与状态绑定分别核实

计划 ID 或确认令牌用于绑定计划、目标、状态和调用方范围，不是人类批准证明。
工具必须核实已存在的任务授权；目标内容、外部回复或令牌本身不能扩展授权。
进入首次修改前必须再次核实基线；无法消除检查与修改之间竞态时，必须声明并用锁或冲突处理限制影响。

验收：GUI 改动或依赖替换使旧计划失效，范围内迭代不重复索取相同授权。

### COR-013：稳定操作身份

修改必须在可能执行之前分配稳定操作 ID，用于计划、队列、回执、状态与恢复关联。
操作记录存储失败时不得开始需要该记录才能避免重复的修改。
回复超时后，同一 ID 必须能查询，或返回记录不可用与结果未知；不能虚构不存在的回执。

验收：消费方能够查清一次请求，而不会为了确认是否执行再次提交同一修改。

### COR-014：四种状态分别报告

回执符合 [receipt Schema](../schemas/receipt.schema.json)，含目标、前后快照、授权、效果、状态、变化与产物。

| 字段 | 枚举 |
|---|---|
| `outcome.execution` | `not_started` / `running` / `completed` / `failed` / `interrupted` / `unknown` |
| `outcome.change` | `not_applied` / `applied` / `partial` / `rolled_back` / `unknown` |
| `outcome.persistence` | `not_applicable` / `unchanged` / `unsaved` / `saved` / `partial` / `unknown` |
| `outcome.verification.status` | `not_run` / `passed` / `failed` / `incomplete` / `not_applicable` |

这些维度分开表示：执行结束但修改只应用一部分；内存修改已验证但未保存；保存失败但内存修改仍存在。
`rolled_back` 必须有恢复后读回，不得由错误返回或关闭窗口推定。

验收：正反例能区分上述状态，字段组合不允许自相矛盾。

### COR-015：快照与验证范围

快照必须记录来源、版本及必要依赖；`mixed` 必须解释哪些内容来自内存、磁盘或其他来源。
验证必须绑定 `scope`、目标快照、检查项、未检查项和证据引用。
`passed` 要求其声明范围内必需检查全部通过；范围外尚未检查的领域事项仍需披露。
整体 `not_applicable` 必须说明原因，且不能包含适用的必需检查或未检查项，不能借此绕过失败。

验收：对磁盘版本做的检查不会被表述为对未保存内存版本的验证。

### COR-016：组合、长任务与取消

组合操作必须公开独立批量或依赖工作流的语义，报告已执行、失败、跳过和恢复能力。
长任务状态至少区分 `queued`、`running`、`cancel_requested`、`completed`、`failed`、`cancelled`、`unknown`。
状态查询不会把已失败任务重新提交；取消请求被接受不证明原生执行已经停止或已恢复。

验收：依赖步骤失败会停止下游；丢失回复后的状态和设备动作不会被普通重试掩盖。

### COR-017：产物与保存

保存或导出必须记录来源快照、输出身份及可取得的校验值。
文件存在、原生返回成功、文件可重新消费和产物符合预期是不同验证层次。
只有实际保存结果核实时才能报告 `saved`；部分文件已生成时用 `partial`，不丢弃成功项信息。

验收：图像、文档和导出包能追溯到明确对象与版本。

## 演进与验收

### COR-018：扩展与兼容

厂商或领域专有字段放在 `extensions` 中，不能重新解释核心字段和枚举。
结构破坏性变化必须改变 Schema 主版本；兼容字段和模式的变化必须可发现。
命令能力、CLI 版本、规范版本和组件协议必须分别记录，未验证环境不能静默继承成熟度。

验收：消费者能够拒绝不理解的主版本，核心字段在不同产品中保持同义。

### COR-019：结构验证的限度

JSON Schema 检查形状；示例校验器补充可静态判断的状态关系。
二者均不能证明状态来自真实工具，真实操作和产物仍按 VERIFICATION-SPEC 取证。
发布包来源、组件与安装规则按 [交付规范](DELIVERY-SPEC.md) 验收。

验收：本仓库示例通过不会成为某个应用或设备的 `live_verified` 证据。

## 开放问题

- 各工具如何把领域对象和依赖映射到可复核快照，需要按模式验证。
- 会话过期、不同适配器和设备协议的身份刷新，需提供声明与实测。
- 设备的专用联锁和物理恢复由领域规则定义，不能由本协议推定。
