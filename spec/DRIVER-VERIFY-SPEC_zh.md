# DRIVER-VERIFY-SPEC

[English](DRIVER-VERIFY-SPEC.md) | 中文

> 版本 1.0.0-rc.1 · 条款 DVER-001 至 DVER-051

## 怎么读

本规范说明驱动工具怎样证明自己能用。每条规则是一个条款，带固定编号，如 `DVER-010`。条款以两行结束：「为什么」说明理由；「检查」说明怎么检查，🤖 表示由测试或脚本自动检查，👀 表示由人在评审时检查。

用词的含义：

- 必须、禁止：硬性要求。违反了，工具就不合规。
- 应该、不应该：默认的做法。只有说得出理由时才能偏离。
- 可以：允许，但不要求。

机器契约 `contract/driver-contract.json` 以数据形式记录测试编号、成熟度等级和证据种类。重复这些值的表格带有契约标记。这类表格与契约不一致时，以契约为准。

## 适用范围

本规范适用于每个驱动工具，也适用于驱动运行时。内容包括：

- 每个工具都要跑的两组一致性测试：通用一致性测试（G 组和 R 组）和驱动一致性测试（D 组）
- 模拟宿主：在这些测试里代替被驱动的软件
- 每条命令都有的行为矩阵
- 每条命令都要声明的成熟度和证据
- 在真实软件上的验收

本规范不重复被测试的规则，每项测试都写明它检查哪些条款。

贯穿本规范的一句话：能测才算数。没运行不等于通过，模拟不等于真实，没核实不等于成功。

## 术语

| 术语 | 含义 |
|---|---|
| 驱动运行时 | 每个工具原样复制的共用代码，实现内置命令、标准命令、写操作流程和回执 |
| 领域命令 | 工具作者自己登记的命令，区别于运行时提供的内置命令和标准命令 |

| 一致性测试 | 本规范两组测试中的一项：通用（G00 至 G10、R01 至 R06）和驱动（D01 至 D23） |

| 成熟度 | 一条命令被证明到什么程度：`draft`、`experimental`、`verified` 或 `stable`（DVER-040） |
| 证据 | 证明成熟度属实的文件，由证据引用指向它（DVER-041） |
| 模拟证据 | 用模拟宿主得到的结果 |
| 真实运行 | 在授权目标上，用真实软件运行工具 |
| 真实软件记录 | 一次真实运行留下的 JSON 记录，放在 `docs/evidence/`（DVER-042） |

| 真实软件验收 | 在真实软件上检查工具，做法写在 `docs/E2E.md` |
| 授权目标 | 人允许真实运行使用的软件实例、文件、文件夹或设备 |

## 运行时与工具的分工

| 方面 | 运行时和 tool-driver-cli-spec 仓库提供 | 工具作者要做 |
|---|---|---|
| 一致性测试 | 两组测试，可以从命令行运行任何工具 | 每次合并和发布时，在每个出包的平台上用 CI 跑这两组测试 |
| 写命令样例 | 使用样例的 G 组测试；内置命令和标准命令的样例 | 为每个领域写命令提供一个有效样例 |
| 模拟宿主 | 模拟宿主，带进程内的适配接口和宿主协议 | 不用写 |
| 行为矩阵 | 固定的行清单 | 每条命令一张矩阵，填写期望结果、实际结果和证据 |
| 成熟度与证据 | `reference` 展示成熟度和证据；`check_project` 核对等级与证据 | 为每条命令声明等级和证据，并让证据保持有效 |
| 真实软件验收 | 契约中的真实软件记录 Schema | 在授权目标上运行；编写 `docs/E2E.md` 和 `docs/evidence/` 下的记录 |

## 通用一致性测试

### DVER-001 一致性测试套件

驱动运行时附带两组一致性测试：通用一致性测试（DVER-003）和驱动一致性测试（DVER-010）。每个工具必须在每次合并和每次发布时，在它出包的每个平台上跑这两组测试（DREPO-041）。工具禁止跳过、削弱或修改任何一项测试，也禁止把某项测试标为预期失败。适用（DVER-010）却没有运行的测试按失败计。这两组测试禁止依赖真实软件、许可或设备，由模拟宿主代替它们（DVER-020）。

为什么：这些测试检查的是每个 Agent 都依赖的规则。跳过一项，坏掉的规则就藏在一次「全部通过」的构建后面。
检查：👀 评审 CI 工作流：两组测试在每个出包的平台上运行，没有跳过或改动任何一项。

### DVER-002 写命令样例

工具必须在 `tests/` 里为每个领域写命令提供一个有效样例。样例是一次调用的参数：命令接受这些参数，带 `--dry-run` 运行时返回有效的预览（G02）。通用一致性测试在各项写操作测试里使用这些样例。内置命令和标准命令的样例由测试套件自带。成熟度为 `draft` 的命令同样需要样例（DVER-040）。

为什么：测试套件猜不出领域命令的有效参数。没有样例，确认相关的测试就没法在这个命令上运行。
检查：🤖 通用一致性测试 G00。

### DVER-003 通用一致性测试

通用一致性测试必须包含下表的各项，每个工具必须全部通过。通过条件里的「没有写入」，指测试用到的文档、文件和设备在测试之后保持不变。最后一列是每项测试检查的条款。

检查：🤖 通用一致性测试 G00 至 G10、R01 至 R06。

### DVER-004 每个命令都被运行过

工具自己的测试必须把每个领域命令和工具提供的每个驱动标准命令（DCLI-200）至少运行一次。测试跑完后，R06 统计这些命令中运行过哪些，有一个没运行过就失败。内置命令（DCLI-030）不含工具代码，由运行时单元测试覆盖（DVER-022）。

为什么：没有任何测试运行的命令，哪次发布坏了都不会有人发现。
检查：🤖 通用一致性测试 R06。

## 驱动一致性测试

### DVER-010 驱动一致性测试

驱动一致性测试必须包含下表的各项，每个工具必须通过所有适用于它的测试。每项测试什么时候适用，契约在 `conformance.driver[].applies_when` 里列出，取值来自 `conformance.applies_when_values`；满足其中任意一个条件，测试就适用：

- `always`：每个工具都适用；
- `writes`：工具有写命令；
- `dangerous`：工具有在危险级运行的命令，哪怕只在某些情况下（DCLI-051）；
- `jobs`：工具有长任务；
- `session` 或 `device`：工具支持该模式；
- `host_component`：工具有宿主组件；
- `physical`：工具有带 `physical` 效果的命令。

哪些测试适用，由运行时根据命令登记判断，不由工具作者决定。不适用的测试报告为不适用，并写明条件。测试运行 CLI 时由模拟宿主代替被驱动的软件，所以结果属于模拟证据（DVER-021）。最后一列是每项测试检查的条款。

| `D02` | 预演之后，实例重连或重启 | 确认被拒绝，`E_CONFLICT` `session_changed` | DCLI-056, DCLI-203 |
| `D03` | 预演之后，文档被修改 | 确认被拒绝，`E_CONFLICT` `document_changed` | DCLI-056, DCLI-210 |
| `D04` | 软件忙 | `E_BUSY`，可重试，`dispatch_state` 为 `not_started` | DCLI-057, DCLI-204, DCLI-276 |
| `D05` | 弹窗挡住了软件 | `E_HUMAN_REQUIRED`，附 `resume` 命令 | DCLI-066, DCLI-204 |

| `D21` | 宿主连续 3 次没有回复心跳 | 会话变为 `lost`；正在进行的写操作记为结果未知 | DCLI-204, DCLI-278 |
| `D22` | 两个实例中有一个不回应 | `session list` 在 5 秒内返回两个实例，不回应的那个实例 `state` 为 `busy` | DCLI-205 |

检查：🤖 驱动一致性测试 D01 至 D23。

### DVER-011 黑盒测试

测试必须把 CLI 当作黑盒：从命令行把它作为单独的进程启动，只根据退出码、stdout 上的信封和模拟宿主收到的内容判断结果。测试禁止导入工具的代码，也禁止直接调用运行时的函数。每次运行必须使用临时的状态目录（DSEC-034）。这样测试就与实现语言无关：用其他语言写的运行时必须原样通过同一套测试（DCLI-263）。

为什么：Agent 只看得到命令行。从内部检查的测试会放过让 Agent 失败的工具，还会把测试绑死在一种语言上。
检查：👀 评审测试代码：每项测试都以进程方式启动 CLI。

## 模拟宿主

### DVER-020 模拟宿主

tool-driver-cli-spec 仓库提供模拟宿主：一个在测试中代替被驱动软件的小程序。它必须同时提供工具接入软件的两种方式：进程内的适配接口（DCLI-260）和完整的宿主协议（DCLI-270 至 DCLI-280）。它也是宿主协议的参考实现（DCLI-281）。它必须能模拟：

- 同时运行的多个实例
- 内存中的文档，以及未保存的修改
- 弹窗、主线程忙和断连
- 人在软件里手动修改文档
- 长任务
- 一台模拟设备，可以处于每一种设备状态（DCLI-230）

测试必须能让模拟宿主进入上面每一种情况，并读取它的状态，从而看出修改有没有到达、到达了几次。

为什么：最要紧的失败，比如弹窗和断连，在真实软件里很少见，也很难按需制造。
检查：🤖 驱动一致性测试 D01 至 D23，它们需要上面每一种情况。

### DVER-021 模拟证据

用模拟宿主得到的结果只证明运行时的机制，比如授权范围检查、确认、操作记录、锁和回执。这些结果属于模拟证据，禁止当作真实软件上的结果展示。只有模拟证据支撑的命令或支持矩阵条目，禁止标为 `verified`（DREPO-022、DREPO-023）。

为什么：模拟宿主的行为是本仓库写出来的，不是软件真实的行为。把两者混在一起，就是声称了从没验证过的支持。
检查：🤖 `check_project`：没有 `live:` 记录的，一律不得标为 `verified`。

### DVER-022 规范仓库 CI 中的模拟宿主

tool-driver-cli-spec 仓库必须在每次合并和每次发布时，在 Windows、macOS 和 Linux 的 CI 上用模拟宿主运行驱动运行时、项目模板、两组一致性测试和评测场景（DSKL-041）。运行时单元测试也必须在同一个 CI 里、在这三个系统上运行。它和两组一致性测试一样是必过的检查：不通过就不能合并，也不能发布。它覆盖内置命令（DVER-004），以及「检查」行引用运行时单元测试的每条规则。

为什么：每个工具都原样复制运行时。在这里发现的问题修一次就够了，不用每个工具各修一遍。
检查：👀 评审 tool-driver-cli-spec 仓库的 CI 工作流。

## 行为矩阵

### DVER-030 行为矩阵

每个领域命令和工具提供的每个驱动标准命令（DCLI-200）都必须在 `tests/` 里有一张行为矩阵。内置命令（DCLI-030）不需要，由运行时单元测试覆盖（DVER-022）。每行是一种情况，记录期望结果、实际结果和证据（证据引用，见 DVER-041）。矩阵必须包含以下各行：

<!-- contract:behavior_matrix_rows -->
| 行 | 组 | 情况 |
|---|---|---|
| `normal` 正常 | 通用 | 一次成功的有效调用 |
| `empty` 空结果 | 通用 | 一次有效调用，但没有可返回的内容 |
| `invalid_input` 无效输入 | 通用 | 参数格式错误或超出范围 |
| `not_found` 找不到 | 通用 | 指定的对象、文档、会话或长任务不存在 |
| `ambiguous` 名字有歧义 | 通用 | 一个名字匹配到多个对象或实例 |
| `conflict` 冲突 | 通用 | 前置条件不满足，比如目标被锁或文档已变 |
| `no_scope` 没有授权 | 通用 | 没有授权范围文件，或授权范围没有覆盖这次调用 |
| `busy` 软件忙 | 驱动 | 软件主线程忙 |
| `dialog` 弹窗 | 驱动 | 弹窗挡住了软件 |
| `disconnect` 断连 | 驱动 | 调用过程中连接断开 |
| `unsaved` 未保存 | 驱动 | 文档有未保存的修改 |
| `read_back_mismatch` 读回不符 | 驱动 | 读回的值与请求不符 |

某一行对这条命令不可能发生时，这一行必须留在矩阵里，并在期望结果一栏写明原因。没有实际结果和证据的行就是没运行过；没运行过的行禁止算作通过。

为什么：Agent 每天都会遇到这些情况。不知道命令在这些情况下怎么表现，它就会在最糟的时候出错。
检查：👀 评审：每个领域命令和标准命令都有矩阵，十二行齐全。

### DVER-031 适配层在真实软件上的行为

模拟宿主无法说明适配层面对真实软件时的表现：能不能识别软件真正的弹窗，读回的是不是软件里真实的值。这些必须在真实软件上运行行为矩阵来检查（DVER-050）。关于它们的结论必须引用真实软件的证据，禁止用模拟证据支撑。

为什么：模拟的弹窗长什么样由测试说了算。只有真实软件才能说明适配层能不能看到它的弹窗、读对它的值。
检查：👀 评审：每条 `verified` 命令的「弹窗」和「读回不符」两行都引用 `live:` 证据。

## 成熟度与证据

### DVER-040 成熟度等级

每条命令都必须声明成熟度等级和支撑它的证据引用，`reference` 会展示这两项（DCLI-031）。等级禁止高于证据能支撑的程度。内置命令的等级由运行时声明，以运行时单元测试为依据（DVER-022）。每一级都需要低一级的全部证据，再加上本级自己的证据：

<!-- contract:maturity_levels -->
| 等级 | 含义 | 需要的证据 |
|---|---|---|
| `draft` | 已声明，接口还可能变 | 无；写命令仍要有样例（G00） |
| `experimental` | 行为矩阵在模拟宿主上通过 | `simulated:` 引用 |
| `verified` | 还在真实软件上运行过并有记录 | 另加当前有效的 `live:` 记录（DVER-043） |
| `stable` | 还通过了评测，没有未关闭的严重缺陷 | 另加当前有效的 `eval:` 报告（DSKL-043） |

证据不再有效时，等级必须降到剩余证据能支撑的最高一级。严重缺陷指让命令对错误的结果报告成功、改动目标或授权范围之外的东西，或者丢失用户数据的缺陷。

为什么：成熟度告诉 Agent 和人能在多大程度上信任一条命令。等级高过证据，就是虚假的承诺。
检查：🤖 `check_project`：`reference` 中每条命令的等级都有该等级所需种类的证据支撑。

### DVER-041 证据引用

证据引用的格式是 `<kind>:<path>[#<anchor>]`。`path` 是相对于工具项目根目录的路径，必须指向仓库里的一个文件。`anchor` 可以省略，用来指明文件中的某一部分，比如真实软件记录里的某个行为矩阵行。`kind` 必须取下表之一：

<!-- contract:evidence_kinds -->
| 种类 | 证明什么 | 文件在哪里 |
|---|---|---|
| `simulated` | 命令在模拟宿主上通过了测试 | `tests/` 中的测试或行为矩阵 |
| `live` | 命令在真实软件上运行过 | `docs/evidence/` 中的真实软件记录（DVER-042） |
| `eval` | Agent 带着工具的 Skill 完成了评测题 | 针对 `tests/eval/` 中评测题的评测报告 `docs/evidence/eval-*.json`（DSKL-043） |

例子：`live:docs/evidence/2026-11-01-footprint-move.json#normal`。

为什么：指向真实文件的引用，让脚本和人都能逐条核对，而不是只能相信。
检查：🤖 `check_project`：每个引用都能解析、种类在表中、指向的文件存在。

### DVER-042 真实软件记录

每次真实运行都必须在 `docs/evidence/` 留下一份 JSON 记录，并符合契约中的证据 Schema。记录包含：

- `kind`：固定为 `live`
- `tool`、`tool_version` 和 `commit`：工具，以及实际运行的那个构建
- `application`：软件的名称和版本
- `os`：操作系统
- `recorded_at`：运行时间，UTC
- `targets`：这次运行使用的授权目标（DVER-050）
- `runs`：每条命令一项，包括命令路径、参数、退出码和 `result`

命令的表现符合预期时，`result` 为 `pass`，否则为 `fail`。某一项在 `matrix_row` 里写明了行为矩阵的行时，预期就是那一行的期望结果。每一项可以另加输出的信封（`envelope`）、它的 SHA-256（`envelope_sha256`）和说明。带机密的参数必须写成 `***`（DSEC-040）。

```json
{
  "kind": "live",
  "tool": "kicad-cli",
  "tool_version": "1.4.2",
  "commit": "3f9c2ab",
  "application": {"name": "KiCad", "version": "10.0.1"},
  "os": "Windows 11 24H2 x64",
  "recorded_at": "2026-11-01T09:30:00Z",
  "targets": ["file:///D:/e2e/demo-board/"],
  "runs": [
    {
      "command": "footprint move",
      "arguments": ["--session", "kicad-1234", "--doc", "D:/e2e/demo-board/board.kicad_pcb", "--ref", "R1", "--x", "12.5mm", "--y", "30mm"],
      "exit": 0,
      "result": "pass",
      "matrix_row": "normal",
      "envelope_sha256": "090b93f6516be82d6d224af36e040f4997faff07f3cda65b9c973520bd833fc3"
    },
    {
      "command": "footprint move",
      "arguments": ["--session", "kicad-1234", "--doc", "D:/e2e/demo-board/board.kicad_pcb", "--ref", "R2", "--x", "15mm", "--y", "30mm"],
      "exit": 7,
      "result": "pass",
      "matrix_row": "busy",
      "notes": "Started during a design rule check; E_BUSY with dispatch_state not_started."
    }
  ]
}
```

为什么：记录写明了版本、参数和结果，任何人都能看出跑了什么，并且能再跑一遍。事后凭记忆写的总结什么也证明不了。
检查：🤖 `check_project` 用证据 Schema 校验 `docs/evidence/` 中的每份记录。

### DVER-043 当前有效的证据

真实软件记录只在它的 `tool_version` 与工具的主版本和次版本都相同时才算证据。评测报告按同样的规则，以报告中写明的工具版本为准。主版本或次版本不同的证据禁止用来支撑成熟度等级。例如工具版本为 1.4.2 时，1.4.0 的记录有效，1.3.9 的记录无效。发布新的次版本或主版本之后，命令要有新的真实软件记录才能保持 `verified`，要有新的真实软件记录和新的评测报告才能保持 `stable`（DVER-040）。

为什么：次版本可能改变行为。旧版本的证据说明不了当前版本。
检查：🤖 `check_project` 把每份记录和报告中的工具版本与 `package.json` 中的版本比较。

## 真实软件验收

### DVER-050 只用授权目标

真实运行必须只使用经人授权、并列在 `docs/E2E.md` 的 Authorized Targets 一节中的软件实例、文件、文件夹和设备。目标只能由人加入这份清单。真实运行禁止触碰任何其他工程、实例或设备。真实运行使用的授权范围文件应该只授予这些目标（DSEC-012），这样运行时会拒绝目标之外的任何写操作。

为什么：真实运行会做出真实的修改。在未经授权的工程或生产机器上，一次测试就可能造成真实的损失。
检查：👀 评审：`docs/evidence/` 中每份记录的 `targets` 里的每一项都列在 Authorized Targets 里。

### DVER-051 验收文档

每个工具都必须在 `docs/E2E.md` 和 `docs/E2E_zh.md` 中说明真实软件验收，按 DREPO-017 规定的章节和顺序来写。这份文档写明授权目标（DVER-050），说明怎样在真实软件上运行行为矩阵（DVER-031），列出真实软件记录的索引（DVER-042），并给出最近一次真实运行的结果。

为什么：评审的人或下一任维护者，需要在一个地方看到跑了什么、在哪里跑、什么时候跑的。
检查：🤖 `check_project` 检查两个文件是否齐全，章节是否完整、顺序是否正确。
