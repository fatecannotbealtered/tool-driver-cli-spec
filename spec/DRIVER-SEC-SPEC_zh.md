# DRIVER-SEC-SPEC

[English](DRIVER-SEC-SPEC.md) | 中文

> 版本 1.0.0-rc.1 · 条款 DSEC-001 至 DSEC-073

## 怎么读

本规范规定驱动工具的安全规则。每条规则是一条条款，有固定编号，如 `DSEC-014`。引用其他规则时只写条款编号。

- 必须、禁止：要求。违反其中任何一条，工具就不合规。
- 应该、不应该：预期的做法。只有说得出理由时才偏离。
- 可以：允许。

有些表格重复了机器契约 `contract/driver-contract.json` 里的值，表格前有一行注释写明对应的契约条目。这类表格与契约不一致时，以契约为准。

每条条款以两行结尾。「为什么」说明理由；「检查」说明怎样检查是否合规：🤖 表示由测试或脚本检查，👀 表示由人在评审时检查。

## 适用范围

驱动工具是让 AI Agent 操作专业桌面软件（如 CAD、EDA、仿真软件）或设备（如机床、仪器）的命令行工具。中心思想是：人划范围，Agent 动手，工具保证每一步做得对、说得清。

本规范规定让这种分工保持安全的规则：

- 命令和工具的风险等级；
- 授权范围文件：人用它决定 Agent 能改什么；
- 来自文档、软件、设备和团队知识的不可信内容；
- 状态目录：工具存放密钥、记录和锁的地方；
- 机密和对外的网络连接；
- 宿主组件的安装和运行；
- 设备上的物理动作；
- 从源码到已安装的包的供应链。

本规范适用于所有驱动工具的所有模式：文件、会话和设备。写操作流程本身（预演、确认令牌、确认时的复查、读回、回执）由 DCLI-050 至 DCLI-067 规定，本规范补充围绕它的安全规则。

## 术语

| 术语 | 含义 |
|---|---|
| 驱动工具 | 让 AI Agent 操作桌面软件或设备的命令行工具。 |
| 驱动运行时 | 每个驱动工具原样复制的共用代码。它实现内置命令和标准命令、授权范围检查、确认、操作记录、锁和回执。 |
| 适配层 | 工具作者写的代码，负责与软件、软件的文件或设备打交道。 |
| 宿主组件 | 工具中装进被驱动软件、由软件加载运行的部分，如插件、加载项、脚本服务。 |
| 效果 | 命令会改变什么。每个命令都要声明效果（DCLI-051）。 |
| 确认级别 | 写操作的确认方式：直接执行、两步确认或危险（DCLI-052）。 |
| 风险等级 | 命令或工具的修改能影响到多远：`T0`、`T1` 或 `T2`（DSEC-001）。 |
| 授权范围、授权范围文件 | 人写在 JSON 文件里的授权：哪些效果、哪些目标、到什么时候。 |
| 目标键 | 一个对象的唯一写法，如 `file:///D:/proj/board.kicad_pcb#/footprints/R1`（DCLI-028）。 |
| 预演 | 带 `--dry-run` 的调用。返回预览，不做任何修改。 |
| 确认令牌 | 预演返回的值，经过签名，只能用一次。确认时原样传回（DCLI-055）。 |
| 操作记录 | 运行时对一次写操作的记录：命令、目标、授权范围 ID、预览、回执和状态（DCLI-059）。 |
| 不可信内容 | 来自文档、软件、设备或团队知识的文字，而不是来自工具或人（DSEC-020）。 |
| 状态目录 | 每个用户一个的目录，运行时在里面存放密钥、记录、锁和缓存（DSEC-030）。 |
| 机密 | 密码、访问令牌或许可密钥。 |
| 模拟设备 | 由软件模拟、不对应真实硬件的设备。 |
| 来源证明 | 一份签名声明，证明某个 npm 包由工具自己的发布工作流构建。 |
| `<tool>` | 工具的命令名，如 `kicad-cli`。 |
| `<PREFIX>` | 工具的环境变量前缀：命令名转成大写、`-` 换成 `_`，如 `kicad-cli` 的前缀是 `KICAD_CLI`（DREPO-053）。 |
| `<state_dir>` | 状态目录的路径。 |

## 运行时与工具的分工

| 方面 | 驱动运行时已经提供 | 工具作者还需要做 |
|---|---|---|
| 风险等级 | 根据效果推导每个命令的确认级别和风险等级，再根据命令推导工具的风险等级 | 为每个领域命令声明全部效果；在 README 和 SECURITY.md 里写明工具的风险等级 |
| 授权范围 | 找到、读取并校验授权范围文件；用它检查每次写操作；在 `context` 里报告状态 | 在 SECURITY.md 里说明人怎样为本工具写授权范围；从不写授权范围文件，也不随工具发布授权范围文件 |
| 不可信内容 | 把软件报错原文、弹窗文字和团队知识列入 `meta.untrusted` | 声明领域命令结果里哪些字段是不可信内容 |
| 状态目录 | 创建状态目录并只允许当前用户访问；在里面存放密钥、操作记录、锁、缓存和登记 | 让每个测试都使用临时状态目录 |
| 机密与网络 | 遮盖已声明的机密；`update` 和 `doctor` 遵守代理设置并校验 TLS | 声明哪些参数是机密；只连接所驱动的软件或设备，遵守代理设置并校验 TLS |
| 宿主组件 | `plugin get`、`plugin install` 和 `plugin remove`；哈希和协议版本校验；版本不一致时拒绝写操作 | 构建宿主组件及其清单；用宿主端小库建立本机连接 |
| 物理动作 | 把物理动作命令定为危险级；检查授权范围；把设备状态转成错误 | 让适配层读取设备的真实状态，包括急停、故障和是否就绪；标明模拟设备 |
| 供应链 | `update` 核对来源证明；从已安装的包里安装和同步 Skill | 维护锁文件；只从由标签触发、带来源证明的发布工作流发布；发布的包没有安装脚本 |

## 风险等级

### DSEC-001 风险等级

每个命令都有风险等级，表示它的修改能影响到多远。

<!-- contract:risk_tiers -->
| 等级 | 含义 | 属于这一级的效果 |
|---|---|---|
| `T0` | 只读，不改任何东西 | `observe` |
| `T1` | 改变软件的运行状态、软件里的对象或本地文件 | `session`、`change`、`artifact`、`persist` |
| `T2` | 修改设置或宿主组件、把内容交给外部的人或系统，或者作用于物理世界 | `configure`、`deliver`、`physical` |

每种效果都有一个最低风险等级，见 DCLI-051 表格中的风险等级一列。命令声明了几个效果，它的风险等级就取这几个最低等级里最高的那一级。运行时必须根据声明的效果推导风险等级。工具只声明效果，不声明等级。

为什么：所有命令按同一条规则排出影响范围，人一眼就能判断任何一个工具。
检查：🤖 运行时单元测试。

### DSEC-002 工具的风险等级

工具的风险等级取 `reference` 列出的全部命令中最高的一级。内置命令按 `observe` 声明（DCLI-030），所以 `update` 和工具自己的状态不会抬高它。`knowledge create` 和 `knowledge delete` 只改工具自己的登记：它们仍然两步确认（DSKL-123），但不计入工具的风险等级。工具必须在 README 的风险等级徽章（DREPO-020）、README 信息卡（DREPO-021）和 SECURITY.md 的 Risk Tier 一节（DREPO-013）里写明这个等级。三处都必须等于根据 `reference` 推导出的等级。

为什么：人在授予授权范围之前，要靠这个等级判断工具需要多小心；徽章标得比命令实际能做的低，就会误导人。
检查：🤖 `check_project` 比对风险等级徽章和根据 `reference` 推导出的等级。

### DSEC-003 不得降级

命令的确认级别和风险等级，都按 DCLI-051 和 DCLI-052 的规则由声明的效果决定，由运行时计算。工具必须声明命令的全部效果；禁止通过设置、自己的代码或修改运行时来降低其中任何一个级别。没有任何条款允许工具降低级别。其他条款允许工具偏离某个默认做法时，`reference` 会写明这项偏离（DCLI-031）。只有人写的授权范围文件能改变确认方式，而且只能改得更严（DSEC-013）。

为什么：如果每个工具都能放松自己的确认，人能否放心就取决于每个作者的判断，而不是一条统一的规则。
检查：🤖 一致性测试 G01 和 G09 运行每个两步确认级和危险级的样例；`check_project` 确认运行时副本没有改动（DREPO-034）。

## 授权范围

### DSEC-010 授权范围文件的位置

运行时从环境变量 `<PREFIX>_SCOPE_FILE` 指定的路径读取授权范围文件。没有设置这个变量时，路径为 `<state_dir>/scope.json`。运行时禁止到其他地方找授权范围：不找当前目录，不找工程目录，也不从命令行参数读取。

为什么：位置固定，才清楚哪份授权在起作用，也能防止授权范围随下载的工程一起混进来。
检查：🤖 运行时单元测试。

### DSEC-011 只由人来写

授权范围文件只由人来写。运行时必须只读取它，没有任何命令会创建、修改或删除它。Agent 禁止创建或修改授权范围文件，也禁止把 `<PREFIX>_SCOPE_FILE` 指向自己写的文件。写操作因为授权不足被拒绝时，Agent 请人扩大授权范围。

为什么：授权范围是人的决定；Agent 能写它，就等于自己给自己授权。
检查：🤖 评测场景 `out_of_scope_change`（DSKL-040）；👀 评审运行时和 Skill。

### DSEC-012 授权范围的字段

授权范围文件是一个 JSON 对象，包含以下字段：

<!-- contract:scope_fields -->
| 字段 | 必填 | 取值 | 含义 |
|---|---|---|---|
| `scope_id` | 是 | 字符串 | 这份授权的名字。确认令牌和操作记录都带着它（DCLI-055、DCLI-059）。 |
| `effects` | 是 | 效果名的非空列表，不含 `observe` | 写操作允许有的效果（DCLI-051）。 |
| `dangerous` | 是 | `true` 或 `false` | 是否允许危险级操作（DCLI-052）。 |
| `targets` | 是 | 目标键前缀的非空列表 | 写操作允许碰的对象（DCLI-028）。 |
| `expires_at` | 是 | 以 `Z` 结尾的 UTC 时间 | 授权到期的时间。 |
| `confirm` | 否 | `always` | 让所有写操作都两步确认（DSEC-013）。 |

读操作不需要授权范围，所以 `effects` 里不允许出现 `observe`。`contract/schemas/scope.schema.json` 以 Schema 的形式写明了这些规则。不符合这些规则的文件，运行时必须视为无效（DSEC-016），比如缺少必填字段、有未知字段、`effects` 里有 `observe` 或未知的效果名、列表为空，或取值类型不对。

示例：人允许 Agent 修改 `D:/proj/board/` 下的电路板文件，包括保存，期限到 2026 年 11 月 9 日 18:00（UTC），并要求每次写操作都两步确认。

```json
{
  "scope_id": "board-rework",
  "effects": ["session", "change", "persist"],
  "dangerous": false,
  "targets": ["file:///D:/proj/board/"],
  "expires_at": "2026-11-09T18:00:00Z",
  "confirm": "always"
}
```

为什么：几个固定字段就能说清改什么、在哪里改、改到什么时候，人不借助工具也能写出来。
检查：🤖 运行时单元测试；`check_spec` 用 `scope.schema.json` 校验 `contract/examples/` 里的授权范围文件示例。

### DSEC-013 只能调严

运行时必须只用授权范围文件把规则调严。设置 `"confirm": "always"` 后，所有写操作都两步确认：直接执行级的命令不带标志运行时，什么都不改，和两步确认级的命令一样返回 `E_CONFIRMATION_REQUIRED`，附带预览和确认令牌（DCLI-053）。危险级命令仍是危险级。任何字段都不能降低确认级别，不能放行确认规则拒绝的写操作，也不能跳过确认时的复查、读回或操作记录。

为什么：想在每一步执行前先看一眼的人可以这样要求，但文件里的任何内容都不能让工具比规则更松。
检查：🤖 驱动一致性测试 D17。

### DSEC-014 目标和效果的匹配

以下几项全部满足时，授权范围才覆盖一次写操作：

1. 命令声明的每个效果都列在 `effects` 里。
2. 操作属于危险级时，`dangerous` 为 `true`。
3. 写操作碰到的每个对象，其目标键都按 DCLI-028 的规范化和前缀规则匹配 `targets` 中的某个前缀。

不碰带目标键对象的命令，比如 `session open` 和 DSEC-017 列出的命令，满足第 1、2 项就算被覆盖。

批量操作中，每个对象都必须被覆盖；有一个对象没被覆盖，整批都不能执行（DCLI-064）。运行时禁止放宽前缀、猜测目标或按对象名称匹配。

为什么：三项合在一起才能框住修改；只看其中一项都会留下漏洞，比如效果对了，文件却错了。
检查：🤖 运行时单元测试；驱动一致性测试 D14。

### DSEC-015 拒绝写操作

每次写操作前，运行时都检查授权范围：预演时、确认时（DCLI-056 第 3 项），以及直接执行级的写操作执行前。授权范围文件缺失、无效、已过期或没有覆盖这次写操作时，运行时必须返回 `E_FORBIDDEN` 拒绝，什么都不派发。`details.scope` 写明授权范围的状态（DSEC-016）和缺什么：某个效果、危险操作的许可或某个目标键。`details.next_action` 让 Agent 请人扩大授权范围。确认时，如果授权范围文件在预演之后改过、但仍然授予这次写操作，则改为返回 `E_CONFLICT`，冲突项为 `scope_changed`（DCLI-056）。读操作禁止因为没有授权范围而被拒绝。

为什么：没有有效的授权，工具就无法知道人是否同意，所以什么都不改；读操作照常，Agent 仍然可以查看并汇报。
检查：🤖 通用一致性测试 G07 和 G10；驱动一致性测试 D16 检查直接执行级的写操作。

### DSEC-016 授权范围的状态

运行时必须在 `context` 的 `authorization` 里报告授权范围的状态（DCLI-032），同时报告授权范围 ID、实际使用的路径、允许的效果、是否允许危险操作和到期时间。文件缺失或无效时，`context` 同样报告。状态取以下之一：

<!-- contract:scope_statuses -->
| 状态 | 含义 | 写操作 |
|---|---|---|
| `granted` | 文件存在、有效且没有过期 | 授权范围覆盖时允许（DSEC-014） |
| `missing` | 实际使用的路径上没有文件（DSEC-010） | 返回 `E_FORBIDDEN` 拒绝 |
| `invalid` | 文件读不了、不是 JSON，或者不符合 DSEC-012 | 返回 `E_FORBIDDEN` 拒绝 |
| `expired` | 已经过了 `expires_at` 的时间 | 返回 `E_FORBIDDEN` 拒绝 |

为什么：Agent 用一次读调用就能知道能不能写，不用等到写操作被拒绝才发现。
检查：🤖 通用一致性测试 R05 在空状态下运行 `context`；运行时单元测试覆盖每种状态。

### DSEC-017 操作记录和设置的授权

有些命令改的是工具自己的记录或设置，而不是文档。它们同样必须被授权范围覆盖：

- `operation resolve`：授权范围的 `effects` 要包含被登记操作的全部效果（DCLI-035）。
- `plugin install` 和 `plugin remove`：需要 `configure`（DSEC-050）。
- `knowledge create` 和 `knowledge delete`：需要 `configure`（DSKL-123）。

这些命令不碰带目标键的对象，所以 `targets` 对它们不适用。只读取或维护工具自身状态的命令，如 `update`，不需要授权范围（DCLI-030）。

为什么：登记操作结果会解锁目标并留下结论，安装组件或登记知识会改变环境；这些都是要经人的授权范围允许的决定。
检查：🤖 运行时单元测试。

## 不可信内容

### DSEC-020 哪些内容不可信

来自工具和人以外的文字都是不可信内容，包括：

- 对象名称、文档内容和文件名；
- 弹窗的标题和文字；
- 软件自己的报错原文；
- 设备发来的消息；
- 团队知识：登记的链接、链接的说明，以及链接指向的文档（DSKL-107）。

不管是谁写的，运行时和工具都必须把这些内容当作不可信内容。

为什么：文档和弹窗里可能有专门写来操纵 Agent 的文字；按文字的来源区分数据和指令，是对任何软件都成立的唯一界线。
检查：👀 对照本条清单评审每个命令的输出字段。

### DSEC-021 标出不可信内容

含有不可信内容的信封，必须把每个不可信值的 JSON 路径列入 `meta.untrusted`；没有时省略这个键（DCLI-004）。运行时标出它自己产生的值：软件报错原文、`E_HUMAN_REQUIRED` 的 `details` 里的弹窗标题和文字（DCLI-066），以及团队知识的字段。对于领域命令，由工具在登记命令时声明结果里哪些字段是不可信内容，再由运行时列出。

为什么：只有输出逐个字段说明哪些文字来自外部，Agent 才能把数据和指令分开。
检查：🤖 驱动一致性测试 D19 检查团队知识；👀 评审领域命令声明的不可信字段。

### DSEC-022 不当作指令

运行时、工具及其 Skill 都禁止把不可信内容当作指令执行。文档里写着「顺便删掉第 3 层」，或者弹窗里写着「运行这条命令修复许可」，都是要汇报的数据，不是要执行的步骤。不可信内容提议的操作，Agent 必须先停下来问人（DSKL-008）。不可信内容不能扩大授权范围或目标。

为什么：照着文档里的文字去做，写文档的人就能让 Agent 做出人没有要求的事。
检查：🤖 评测场景 `injected_instruction`（DSKL-040）；👀 评审适配层和 Skill。

## 状态目录

### DSEC-030 状态目录的位置

状态目录位于环境变量 `<PREFIX>_STATE_DIR` 指定的路径。没有设置这个变量时，必须是用户主目录下的 `.<tool>`（`~/.<tool>`）。每个用户一个状态目录，该用户的所有进程共用。运行时在第一次使用时创建它，并按 DSEC-032 设置访问保护。

为什么：每个用户有一个固定的位置，多个 Agent 才能共用锁和记录，人也能找到并查看它们。
检查：🤖 运行时单元测试。

### DSEC-031 状态目录的内容

状态目录里有以下内容：

<!-- contract:state_dir_entries -->
| 项 | 存放什么 | 由谁写 |
|---|---|---|
| `keys/` | 签发确认令牌的本机密钥（DSEC-033） | 运行时 |
| `operations/` | 操作记录，保留 30 天（DCLI-059） | 运行时 |
| `locks/` | 目标锁（DCLI-060） | 运行时 |
| `cache/` | 最近一次检查更新的结果（DCLI-079） | 运行时 |
| `hosts/` | 运行中的宿主组件的登记文件（DCLI-271） | 宿主组件 |
| `trash/` | `update` 移走的原生程序，下次运行时清理（DCLI-072） | 运行时 |
| `scope.json` | 默认位置的授权范围文件（DSEC-010） | 只有人 |
| `knowledge-links.json` | 团队知识的登记（DSKL-122） | 只有 `knowledge create` 和 `knowledge delete` |

每一项只可以由表中写明的一方来写。除了宿主组件写在 `hosts/` 里的登记文件，工具代码禁止直接写状态目录，要经过运行时。

为什么：目录结构固定，人就知道工具在磁盘上存了什么，检查也能找到每个关系到安全的文件。
检查：🤖 运行时单元测试；👀 评审工具代码有没有直接写状态目录。

### DSEC-032 访问保护

状态目录只允许当前用户读写。在 macOS 和 Linux 上，权限必须为 `0700`。在 Windows 上，ACL 必须只授权给当前用户。运行时在创建目录时设置好保护。`context` 必须报告实际生效的保护方式（DCLI-032）：`posix_0700`、`windows_acl` 或 `none`，而不是预期的保护方式。

为什么：目录里有令牌密钥、默认位置的授权范围文件和每次修改的记录；其他用户能写这里，就能伪造令牌或扩大授权范围。
检查：🤖 运行时单元测试。

### DSEC-033 令牌密钥

运行时用存放在 `keys/` 里的本机密钥签发确认令牌（DCLI-055）。密钥禁止离开状态目录，也禁止出现在任何输出、日志或记录里。没有密钥时，运行时新建一个；用旧密钥签发的令牌随之失效，返回 `token_invalid`。密钥读不了、已损坏或无法创建，就是不可用。密钥不可用时，所有写操作都以 `E_IO` 拒绝，什么都不派发；读操作照常（DCLI-059）。

为什么：伪造或重放的令牌会跳过预演。密钥不可用时，运行时分不清真令牌和伪造的令牌，拒绝写操作是唯一安全的做法。
检查：🤖 一致性测试 G08。

### DSEC-034 测试用临时状态目录

测试禁止读写用户真实的状态目录。每次测试都必须把 `<PREFIX>_STATE_DIR` 设为新建的临时目录，并且要么把 `<PREFIX>_SCOPE_FILE` 指向这个目录里的授权范围文件，要么从测试环境里去掉这个变量。

为什么：真实的状态目录里有人的授权范围、锁和记录；测试碰到它们，可能授出权限、释放锁或掩盖真实的操作。
检查：👀 评审测试的准备代码。

## 机密与网络

### DSEC-040 机密

机密禁止出现在输出、日志、操作记录、错误信息和真实软件验收记录（DVER-042）里。回显输入的地方，比如预览的 `inputs`（DCLI-054），机密必须显示为 `***`。工具在登记命令时声明哪些参数是机密，由运行时遮盖。

为什么：输出、记录和日志会被 Agent 读取并留在磁盘上；机密一旦写进去，之后读到的人都能看到。
检查：🤖 运行时单元测试；👀 评审声明为机密的参数。

### DSEC-041 对外连接

工具必须只连接以下地址：

- npm 仓库，只由 `update` 和 `doctor` 访问（DCLI-079）；
- 工具所驱动的软件服务或设备，只由驱动它们的命令访问。

工具禁止发送任何遥测数据。与宿主组件的连接只在本机（DSEC-054）。

为什么：人在授权时要能判断数据会去哪里；工具私自往外报数据，可能把设计资料带出公司。
检查：🤖 驱动一致性测试 D19 确认知识命令不发网络请求；👀 评审运行时和适配层的每一处网络调用。

### DSEC-042 团队知识由 Agent 读取

团队知识的文档由 Agent 自己用 lark-cli 读取（DSKL-110）。工具禁止连接飞书，也禁止保存飞书账号或凭证。对团队知识，工具只保存登记的链接（DSKL-105）。

为什么：团队文档的登录和权限属于人自己的飞书工具；驱动工具保存飞书账号，就有泄露的风险。
检查：🤖 驱动一致性测试 D19。

### DSEC-043 代理与 TLS

所有网络请求都必须遵守环境变量 `HTTPS_PROXY`、`HTTP_PROXY` 和 `NO_PROXY`。每个 TLS 连接都必须校验服务器证书。工具禁止提供关闭证书校验的参数、设置或环境变量。

为什么：工具运行在公司网络里，要经过代理；不校验证书，路上的任何人都能篡改更新包或发给设备的命令。
检查：👀 评审运行时和适配层的网络代码。

## 宿主组件

### DSEC-050 安装宿主组件

宿主组件必须只通过 `plugin install` 和 `plugin remove` 安装、升级或卸载（DCLI-240）。两者都是效果为 `configure` 的两步确认级写操作，所以需要允许 `configure` 的授权范围（DSEC-017）。`update`、领域命令和 npm 安装过程都禁止安装或改动宿主组件；需要重装时，`update` 和 `doctor` 给出 `plugin install` 命令（DCLI-079）。

为什么：宿主组件在人的软件里运行，拥有软件的全部权限；把它装进去会改变环境，必须经人允许，并让人看得到。
检查：🤖 运行时单元测试；👀 评审确认 `update` 和 npm 包不安装宿主组件。

### DSEC-051 安装前的校验

安装宿主组件之前，`plugin install` 必须检查：

1. 每个文件都与宿主组件清单里记录的哈希一致；不一致时什么都不装，返回 `E_INTEGRITY`；
2. 清单里的协议版本与 CLI 的协议主版本相同（DCLI-280）；不同时什么都不装，返回 `E_PROTOCOL`。

每个版本装到以版本号命名的单独目录里。旧版本留在磁盘上，直到没有任何运行中的实例加载它为止。

为什么：软件里装进被改动的文件或不兼容的协议，会损坏工作成果或留下漏洞；各版本分目录存放，运行中的实例就能继续使用它已加载的文件。
检查：🤖 运行时单元测试。

### DSEC-052 不重启实例

工具禁止为了升级宿主组件而重启、重新加载或关闭人的软件实例。正在运行的实例继续使用它已加载的版本，直到人自己重启或重新加载。

为什么：重启实例可能丢掉未保存的修改，还会打断正在使用它的人。
检查：👀 评审运行时的 `plugin install` 和宿主组件。

### DSEC-053 版本不一致

`context` 和 `doctor` 必须报告磁盘上的宿主组件版本，以及每个实例已加载的版本。某个实例加载的版本与磁盘上的不同时：

- `doctor` 的 `plugin` 检查失败；
- 发往这个实例的写命令在派发前就被拒绝，`dispatch_state` 为 `not_started`，错误为 `E_HUMAN_REQUIRED`，`action` 为 `restart_application`，请人重启或重新加载这个实例。

为什么：宿主组件与 CLI 预期的版本不同，可能做出 CLI 无法读回、也无法如实报告的修改。
检查：🤖 驱动一致性测试 D12。

### DSEC-054 只接受本机连接

宿主组件必须只用 DCLI-270 规定的本机连接方式：Windows 上用命名管道，macOS 和 Linux 上用 Unix 套接字，只允许当前用户访问。宿主组件禁止开网络端口。每个连接都先按 DCLI-273 握手，协议主版本不同时，在发出任何修改之前就结束连接。宿主组件应该用宿主端小库完成这些工作（DCLI-281）。

为什么：宿主组件能改动软件里的任何东西；网络或其他用户能连上的端口，会让别人也能驱动它。
检查：🤖 驱动一致性测试 D20 检查握手；👀 评审宿主组件的连接方式。

## 物理动作

### DSEC-060 物理动作是危险级

带 `physical` 效果的命令一律是危险级，不管它还声明了什么效果。它必须先带 `--dry-run`、再带 `--confirm` 运行，两次都加 `--dangerous`（DCLI-052、DCLI-053）。授权范围必须在 `effects` 里列出 `physical`，把 `dangerous` 设为 `true`，并覆盖对应的设备目标，如 `device:cnc-01/axis-x`（DSEC-014）。缺少其中任何一项，运行时都会拒绝，设备不会动。

为什么：机器运动或电路通电可能伤人或损坏设备，而且做了就无法撤回。
检查：🤖 驱动一致性测试 D14。

### DSEC-061 先检查设备

派发物理动作之前，运行时必须通过适配层从设备读取当前状态，禁止使用缓存的状态。设备处于 `emergency_stop` 或 `fault`，或者报告还没准备好执行这个动作时，命令必须返回 `E_HUMAN_REQUIRED`，`action` 为 `confirm_on_device`，并给出 `resume` 命令（DCLI-066），什么都不派发。命令禁止等设备自己恢复。`busy` 和 `offline` 两种状态按 DCLI-230 返回对应的错误。

为什么：机器停下来总有原因，必须由人去看；Agent 看不到机器。
检查：🤖 驱动一致性测试 D23；运行时单元测试。

### DSEC-062 模拟结果

设备是模拟设备时，它产生的每个结果都必须标明这一点：设备对象带 `simulated: true`（DCLI-230），在它上面运行的每个命令的结果也带 `simulated: true`。工具、Skill 和 Agent 的汇报都禁止把模拟结果说成真实结果。模拟设备的结果只算模拟证据（DVER-021）。

为什么：在模拟器上跑通，说明不了真实机器上的情况；把它说成真实结果，会掩盖风险。
检查：🤖 驱动一致性测试 D15。

## 供应链

### DSEC-070 锁定依赖

工具必须用放在仓库里的锁文件固定全部依赖的版本，CI 必须按这些锁文件构建。

为什么：没有锁文件，构建可能悄悄引入另一个版本的依赖，甚至是被篡改过的版本。
检查：👀 评审仓库和 CI 的构建步骤。

### DSEC-071 由 CI 发布并带来源证明

工具的每个 npm 包，包括主包和每个平台包，都必须带来源证明，证明它由工具自己的发布工作流构建。所以发布只能在由标签触发的发布工作流里进行，不能在任何人自己的电脑上进行（DREPO-043）。`update` 安装后核对来源证明，如实报告 `verified` 或 `not_checked`（DCLI-074）。

为什么：有了来源证明，任何人都能核对已安装的包是从打了标签的源码构建的，而不是由持有发布令牌的某个人做出来的。
检查：👀 评审发布工作流；`update` 每次安装后都会报告 `provenance_status`（DCLI-074）。

### DSEC-072 没有安装脚本

工具的 npm 包，包括主包和每个平台包，禁止有安装脚本（`preinstall`、`install` 或 `postinstall`），安装时也禁止下载任何东西。工具需要的一切都在它的包里（DREPO-051）。

为什么：安装脚本在任何人看过工具之前就以用户的权限运行，安装时下载的内容也逃过了来源证明的核对。
检查：🤖 合并门槛中的 npm 包内容检查（DREPO-041）。

### DSEC-073 Skill 来自已安装的包

Skill 必须只从已安装的 npm 包里安装和同步（DSKL-031、DCLI-076）。工具禁止从网络拉取 Skill。

为什么：Skill 会引导 Agent 的行为；从别处拉来的副本可能带着工具作者从没写过、来源证明也从没核对过的指令。
检查：👀 评审运行时里安装和同步 Skill 的代码。
